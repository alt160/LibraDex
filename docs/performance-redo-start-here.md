## Current State

This is the restart anchor for the active LibraDex performance redo. Start here before editing harness code, changing shape implementations, or rerunning performance proofs.

**2026-07-13 VS8 scoop-count checkpoint:** the production shelf scoop and required topology repair are complete. Count traversal now aggregates physical route entries by target, applies exact key-slot counting only at range edges, adds persisted live counts for contained shelves/terminal chains, and retries across mutation-version changes. The public encoded-key fixture exposed unsafe compressed-stem rollover, so live VS8 transforms now create expanded exact-stem chains whose sibling routes acquire independent shelves lazily. The final `250,000`-row persisted topology has `35` routers, `152` extents, zero aliases/parents/cycles/overlaps, and exact route/reader order parity. Three isolated ShapeBench processes per engine returned `ResultItems=799,916`; LibraDex median was `26,056.554 ops/s`, SQLite median `6,138.714 ops/s`, or `4.245x`. The original row was `347` versus `17,699` (`0.02x`). See [vs8-scoop-range-count-design.md](vs8-scoop-range-count-design.md).

**2026-07-13 VS16/VV scoop adoption:** both variable-key siblings now use the production scoop, expanded exact-stem live transforms, lazy independent sibling shelves, and serialized complete parent-run republishing. The public count APIs now call the shape-native counters instead of opening readers. Three-process medians with exact `ResultItems=799,916` parity are VS16 `41,090.975 ops/s` versus SQLite `14,221.882` (`2.889x`) and VV `88,342.875` versus SQLite `14,860.940` (`5.945x`). Fixed-N counters already use boundary scans plus contained shelf metadata; fixed-key routing remains unchanged pending a repeated-transform topology inspector because its shared below/above-stem targets need proof, not assumption.

**2026-07-19 FS32 range-reader checkpoint:** FS32-8/16 readers now probe the session's existing promoted direct-router projection before authoritative first-touch target classification. This removes repeated router-file classification without adding a pointer cache, persisted count, or second traversal model. All 18 focused identities/keys/pairs cells passed exact `799,916` parity and LibraDex improved `1.426x-2.643x` versus the replaced canonical rows (`1.978x` median). Trace-attributed in-range classifier time fell `98.26%`. The new focused SQLite ratios are unusually high because those SQLite samples were slower and both engines showed material spread; use LibraDex before/after plus trace for attribution. See `docs/shapebench-performance-continuation-restart.md` and `artifacts/shape-bench/fs32-range-promoted-first-final-20260719/`.

**2026-07-19 canonical warm-session reset:** the prior canonical read runner measured separate cold-start processes and is superseded for final comparison. The corrected runner builds separately, opens one fresh measurement catalog/session or unpooled SQLite connection, discards one cold pass, then records three warm passes in the same open session with fresh per-pass readers/commands. Warm mean is primary; median/min/max/spread and cold rate remain visible. The canonical root was reset to `0 / 291`, its prior files were archived in place, and campaign `canonical-read-warm-t1-250k-3rep-20260719` is running serially from `SS8-8` with incremental HTML and 15-minute monitoring.

The current task is to rebuild the performance evidence after recent concurrency, grouping, fixed-N, and SQLite-comparison work. ## Benchmark Baseline Policy

The performance-redo matrix is now batch-first. Older rows stay visible as evidence, but parity conclusions should come from regenerated rows that follow these rules.

- 🟩 [x] Primary SQLite comparison rows must use batched LibraDex writes and matching SQLite transaction cadence. If LibraDex publishes every `X` items, SQLite commits every `X` items.
- 🟩 [x] Primary write rows must name cadence explicitly: `direct-fullbatch`, `coalesced-fullbatch`, `coalesced-microbatch256`, `coalesced-microbatch1024`, etc.
- 🟩 [x] Primary batch tiers are `256` for small/low-RAM batches, `1024` for standard batches, `4096` for sustained-throughput batches, and full-batch for known fixed units.
- 🟩 [x] Primary read rows must return meaningful volume. Tiny/single-key rows are diagnostics unless fanout is high enough to amortize fixed setup.
- 🟩 [x] Range-read rows must identify whether they are one repeated hot window or rotating windows. Rotating windows are preferred for real-world range evidence.
- 🟩 [x] Rows below SQLite are red focus rows. Rows near SQLite are yellow watch rows. Rows well above SQLite are green unless storage, read bytes, RAM, or allocations explode.
- 🟩 [x] Prior pre-policy numbers are not deleted, but they are no longer authoritative current values until rerun under this policy.

## 2026-07-16 Concurrent-Write Test Realignment

The prior ShapeBench concurrent-batch rows used a shared next-chunk claim counter. That made total throughput measurable, but it did not measure caller concurrency honestly: fast workers could claim most of the `250,000` items while slow workers completed very little. The most visible example had one 8-thread worker process `215,000` items, so its apparent best-thread/single result was mostly work ownership rather than independent caller speed.

The corrected strategy now uses:

- fixed equal item ownership per worker;
- a synchronized start gate after worker construction and input allocation;
- the same `250,000` unique tuples for LibraDex and SQLite;
- `disjoint` key ranges for independent routing/shelf domains;
- `mixed` locality with private ranges plus an interleaved shared range;
- `overlap` locality with every worker interleaved across the same full key range;
- separate one-thread baselines for `BeginConcurrentWriter` and each real `BeginConcurrentBatch` size;
- no artificial batch-size matrix for `BeginConcurrentWriter`, because that public API has no batch boundary;
- LibraDex-first HTML reporting for aggregate/single, average-thread/single, best-thread/single, fairness, active writers, and publication fragmentation.

The corrected run is [report.html](../artifacts/shape-bench/index-redo12-20260711-2350/report.html) with `1,035` unique rows, including `63` concurrency rows. All concurrency rows returned exact `250,000` cardinality, every fixed worker received the same item count, all requested workers were active, stderr was empty, and no child work tree remained.

### Current Performance Opinion

- `BeginConcurrentBatch` demonstrates real independent-domain concurrency. For `SS8-8`, disjoint aggregate throughput is `1.87x-2.48x` the matching one-thread baseline across batch sizes and thread counts.
- Eight mixed callers remain useful at `1.09x-1.35x` single aggregate throughput. Sixteen mixed callers overrun the available independent domains and fall to `0.34x-0.60x`.
- Full overlap is a capability/stability case rather than a speedup case: aggregate throughput is `0.37x-0.84x` single.
- Publication fragmentation is the strongest explanatory metric. Disjoint rows preserve `34.0-162.9` items/publication; contended 16-thread mixed/overlap rows can fall to `1.8-3.1`, directly matching the throughput collapse.
- Generic `BeginConcurrentWriter` currently provides stable concurrent admission, not parallel throughput scaling. Its median aggregate/single ratio across six fixed-scalar shapes is `0.99x`; shape medians range from `0.91x` to `1.05x`. Overlap is weaker, but every caller continues to make progress.
- The capability is unusual and valuable when callers write independent shelf/router domains through `BeginConcurrentBatch`. The current queued-writer facade should be described more conservatively: it avoids a caller-owned global serialization funnel, but its internal single-insert admission remains broad enough that aggregate throughput stays near one-thread speed.

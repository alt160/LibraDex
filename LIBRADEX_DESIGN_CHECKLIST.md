# LibraDex Design Checklist

## 0. Restart Here

**Current focus:** public selection API reset after the data-retrieval facade purge. The old direct index retrieval grammar (`index.Find(...)`, `index.Between(...)`, `index.Prefix(...)`, `index.Keys`, `index.IDs`, `index.Not`, `index.Aggregates`, and related query descriptor types) is no longer exported, and the non-generic `IIndex.Criteria` builder has been removed so adopted conditions cannot route through the old criteria surface. The active direction is to copy, adopt, and modify AbraxasDB's condition builders and index builders so the public selection contract is the Abraxas-style builder grammar mapped onto LibraDex identity-group indexes and encoded primitives. The first adopted builder landing is `LibraDexCondition.ForGroup(...).Index(...).AsType.Operator(...).AND/OR...EndCondition`, which records index-name leaves, classifies each leaf as index-backed/projection-backed/composite-backed/visible-scan-like/unsupported/unresolved, plans the next bridge action for each leaf, and materializes through internal condition retrieval leaves when supplied opened indexes. Classification and bridge planning now cover numeric exact/boundary/membership, folded-text projection, visible scan-like text containment/pattern intent, structured date projection, GUID segment/text projection, binary byte-slice predicates, typed binary-slice predicates, composite descriptors, missing index names, and identity-group mismatches. The structured date codec is now the first executable Abraxas-compatible condition bridge. The adopted date branch matrix covers the unique Abraxas `DateTime`/`DateOnly` branch surface: full-value comparison/membership, year equality/membership/range/boundary, year-month and year-month-day tuples, year-with-months, year-quarter, relative UTC day/hour/minute windows, component-only month/day/quarter/calendar predicates, weekday/weekend, and time-of-day predicates. Executable single-extent branches materialize as one ordered range, while ordered negations such as `NotEqualTo`, `NotBetween`, `YearNotEqual`, and `YearNotRange` now materialize as lower/upper ordered extent unions instead of complement-universe materialization. Repeated year/month/day tuple branches now materialize as a condition-derived same-index `MultiRange` primitive instead of `OR` over scaffold `Between` leaves, so `YearIn`, `YearMonthIn`, `YearMonthDayIn`, and `YearInMonths` expose the real physical need. Component-only branches such as `MonthEqual`, `DayRange`, `SameDayEveryYear`, quarter/half/month boundary checks, weekday/weekend, and `DateTime` time-of-day now execute through a condition-derived `StructuredComponent` primitive that reads packed scalar fields by shift-and-mask. `TimeOnly` semantic branches remain more efficient as structured time ranges: `IsMorning`, `IsAfternoon`, and `IsEvening` are single ordered ranges, while `IsNight` is a two-range midnight wraparound `MultiRange`. GUID exact equality, text equality, inequality, starts-with, ends-with, contains, and full wildcard pattern branches now execute over encoded GUID keys: exact branches use ordinary key primitives and partial/pattern branches use a condition-derived `GuidPattern` primitive that compares canonical GUID nibbles against stored GUID bytes without per-row text conversion. Fixed-width binary equality, starts-with, ends-with, contains, and slice-equality branches now execute over encoded `byte[]` keys: exact branches use ordinary key primitives and partial/slice branches use a condition-derived `BinaryPattern` primitive that compares stored key bytes without per-row byte-array decoding. The binary category now also covers Abraxas-compatible typed binary slices through condition-derived `BinaryTypedSlice`: signed/unsigned integer widths through 128-bit, `BigInteger`, `Single`, `Double`, `Decimal`, `Guid`, `DateTime` ticks, `DateOnly` day number, `TimeOnly` ticks, `TimeSpan` ticks, `DateTimeOffset` ticks-plus-offset normalized to UTC `DateTime`, UTF-8/UTF-16/UTF-32/ASCII/Latin1 strings, caller-supplied `Encoding` instances, UTF-16 char, and UTF-32 rune. Numeric and date/time slices use Abraxas-compatible little-endian interpretation. Fixed and custom encoded string slices use ordinal text comparison; custom encoding slices retain and use the supplied .NET `Encoding` instance directly because LibraDex has no managed/native boundary to cross. Projection-backed string retrieval now has durable physical folded, sort-key, and reversed folded proofs through `LibraDexStringScalar8Index`: exact strings, folded strings, culture-specific sort-key bytes, and reversed folded strings can be written to paired `VS8` raw variable-key indexes, and catalog metadata records the owned folded/sort-key/reversed-folded projection slots, projection cultures, and the standard 1024-byte physical var-key cap needed to reopen the logical string facade. Adopted case-insensitive `StartsWith`, `EndsWith`, and comparison/range conditions resolve through maintained projections before and after file reopen. String conditions also have the first executable scan-backed fallback: exact-only no-case `StartsWith` can generate ordered exact-key candidate ranges from simple case variants, scan only those ranges, and apply .NET culture-aware residual prefix comparison over decoded indexed keys. Broader string resolver conventions, case-sensitive exact reversed suffix projection, and wider scan-backed string operators remain open. The date/GUID/binary branches do not require separate `createdYear`, `createdMonth`, `createdDay`, `createdHour`, GUID text, or binary projection indexes for the currently executable range-shaped, component-mask, GUID-pattern, binary byte-slice, or typed binary-slice branches. Programmable fixed-length sizing is an index construction/open contract only; conditions select values and never carry fixed-N or BigInt storage sizing knobs.

**Current layer:** public facade and adapter layer over the existing internal primitive read spine. The physical varlen and fixed-shape work remains valid, but the active design constraint is that higher-level systems should target adopted condition/index descriptors rather than direct index retrieval methods or the temporary LibraDex-only criteria vocabulary.

**Recent retrieval closure:** scalar condition bounds now use finite CLR key domains (`bool`, narrow numerics, `char`, signed/unsigned scalars, `DateTime`/`DateTimeOffset`/`DateOnly`/`TimeOnly`/`TimeSpan`) for all-range and exclusive predecessor/successor movement, while `byte[]` and `Guid` keep raw encoded bytewise bounds. This prevents condition-derived `After`/`Before`/all-range primitives from decoding invalid sentinels or aliasing values such as `true` when the public type is narrower than the stored 8-byte lane.

**Recent DateTime encoding closure:** DateTime-like indexes now carry an explicit index-level `DateTimeKeyEncoding` contract. The default `CalendarSdt` preserves the Abraxas-compatible structured date/time layout optimized for common calendar filtering, while `PrecisionSdt` preserves full tick precision by using the low bits that `CalendarSdt` spends on direct day-of-week storage. The condition builder remains encoding-agnostic: materialization consults the executing index metadata, exact/range boundaries use the selected encoding quantum, and day-of-week predicates over `PrecisionSdt` derive the weekday from packed year/month/day fields instead of failing or reverting to text conversion. Catalog metadata version 7 persists the main index and composite-part DateTime encoding selector, generic batch inserts now use the owning index encoder so writes and reads share the same SDT contract, routed composite date predicates honor the composite part's DateTime encoding metadata during structured component extraction, and full-key composite byte-domain matching uses the selected part descriptor when encoding DateTime-like operands. The public-surface harness proves in-memory PrecisionSDT equality/boundary/day-of-week behavior plus file-backed reopen for scalar PrecisionSDT metadata, composite DateTime part metadata, and full-key DateTime part matching.

**Recent scalar proof closure:** `artifacts/condition-query-intent-proof.md` now promotes the mapped scalar, enum-as-scalar, and bitmask rows for signed and unsigned integer domains, narrow numerics, `char`, `bool`, UInt32/UInt64/Byte/Int32 bitmasks, and a cross-index bitmask-plus-string case to `Tested Pass`. The new deterministic public-surface fixture asserts exact materialized identities rather than only condition syntax, and the planner now scopes single-index complements such as `NotInSet` to that index's own `All` primitive before using the broader identity-group universe for true multi-index negation.

**Recent DateTime proof closure:** the deterministic structured-date fixture now covers the remaining mapped DateTime retrieval rows: exact `GreaterThan`, exact `Between`, deferred exact cutoff rematerialization, `IsYesterday`, rolling last-days/hours/minutes windows, `YearEqual`, and exact `DateTime.MaxValue` sentinel equality. These rows now have materialized identity assertions in `public-surface-api-sanity` instead of syntax-only mapping.

**Recent GUID proof closure:** the adopted GUID fixture now explicitly covers set membership over GUID values, first-segment prefix matching through the existing GUID pattern primitive, and `Guid.Empty` sentinel exclusion. The membership path reports the current `InSet` primitive, matching the earlier decision that `In(...)` and `InSet(...)` collapse to one set-oriented execution route inside LibraDex.

**Recent string proof closure:** the deterministic string fixture now covers exact and no-case equality, exact and no-case prefix, exact and no-case suffix, exact and no-case contains, `*`/`?` wildcard matching, exact membership, no-case membership through an index-level policy, null-string equality through the string sentinel-byte key contract, empty-string equality through the string sentinel-byte key contract, null/empty ordering, folded equality projection, and reversed suffix projection. Digit-class pattern syntax such as `??-####` remains a policy row because current wildcard grammar only treats `*` and `?` specially. String keys use `0x00` for null, `0x01` for `string.Empty`, and `0x02 + UTF-8` for non-empty strings, so null and empty both sort before non-empty values while remaining distinct. String varlen indexes use the standard hard physical var-key cap of 1024 bytes per key entry; there is no public per-string-index key-length tuning knob. Configurable byte sizing belongs to programmable fixed-length index construction, such as fixed-N/BigInt-style index actors, and must not appear as query or condition semantics.

**Recent composition/terminal proof closure:** the deterministic composition fixture now covers composite scalar range, composite multi-part text, composite missing-leading-tier scan, composite later-tier text prefix, cross-index `AND`, same-index membership as `OR`, cross-index string `OR`, parenthesized/grouped logic, condition-terminal `take`, `Exists`, `Count`, grouped counts, duplicate groups, singleton groups, representatives, and count-descending top-N groups. The fixture deliberately uses opened index actors for storage shape choices and keeps adopted condition expressions free of programmable fixed-length or varlen sizing knobs.

**Recent condition-DX normalization:** hand-written composition and programmatic/multi-key composition are alternate construction ergonomics over the same condition descriptor tree. Opened-index syntax such as `age.Where.GreaterOrEqual(18).AndAlso(status.Where.EqualTo(1))` is the low-friction form for ordinary handwritten code and reusable fragments. Ordered `MultiKey(...)` syntax such as `people.MultiKey(age, status).Where(0).AsInt32.GreaterOrEqual(18).AndAlso(1).AsInt32.EqualTo(1)` is the low-friction form for generated or programmatic code that naturally carries index arrays, ordinals, or loop-selected participants. Both forms normalize to the same `AND`/`OR`/`EXCEPT` tree of index-name leaves inside one identity group; the executor/planner, not the syntax used to build the tree, chooses whether a primitive, projection, scan-like fallback, or available composite/tiered route is the best physical retrieval path.

**Recent catalog condition DX correction:** catalog-group handwritten conditions are now index-first. Use `catalog["customers"].Where("firstName").AsString.StartsWith(value).EndCondition` and continue multi-index conditions with `.AndAlso("otherIndex").AsInt64...` or `.AndAlso(otherIndex).AsInt64...`. Type-first named and handle selectors such as `catalog["customers"].Where.String("firstName")` are retired; only ordered `MultiKey(...)` programmatic ordinal selectors such as `.Where(0).AsString` / `.AndAlso(1).AsString` remain.

**Open filter-DX complaints:** `LIBRADEX_FILTER_DX_COMPLAINTS.md` tracks the active corpus/API complaints. Recent resolved items added `.Matches(...)` short aliases, regex-backed captured-match operators such as `.MatchesWith(...)` / `.MatchesIn(...)` / `.MatchesInSet(...)` plus negations, explicit `NullKey` overloads for null/empty key-state conditions, and corrected F026 plus numeric measurement rows F101-F104. Current open items are to keep auditing corpus rows where measurement/domain values may have been generated as `.AsString` and to confirm any future string operator additions preserve the same case/culture options as the existing string family.

**Recent key-state route anchor:** null/empty special routes cannot be represented as magic root-router prefix bytes because the direct root router owns all 256 normal byte prefixes. They also should not steal fixed-shelf slot bits: `0` is already the deleted-slot sentinel, high-bit stealing would shrink the 64 KiB shelf address domain, and low-bit stealing is unsafe for programmable fixed-N odd item sizes. Catalog metadata version 8 now carries durable `NullKeyRouteOffset` and `EmptyKeyRouteOffset` fields as the non-breaking root-level route anchor. Compact 4 KiB identity-only key-state shelves now exist for scalar-8 and scalar-16 identities: the shelf stores sorted identities only, with no key payload and no slot indirection, because the metadata route itself owns the null-or-empty key state. The agreed enumeration order is null route first, empty route second, then ordinary value routes. This storage and condition slice is proven by `keyRouteMetadataContract`, including route offset publication, sorted scalar-8/scalar-16 identity insertion, duplicate no-op handling, explicit `ScalarNull.Null` / `ScalarNull.NonNull` condition materialization, and reopen reads. Scalar key families may publish a null route but must not publish an empty route.

**Website positioning note:** SQL-family engines often store duplicate index entries with an internal row anchor such as rowid, heap TID, RID, clustered key, or primary key suffix, but SQL query result ordering is not guaranteed unless the query states `ORDER BY`. LibraDex can make index-natural order an explicit product contract because the index is the public object being read, not only an optimizer-selected access path. For a `CreatedDate -> FilePath` index, LibraDex can naturally and stably return `CreatedDate` order with `FilePath` / identity as the tie-breaker while avoiding a separate sort when the caller asks for plan-natural order. This is both intuitive and performance-relevant, especially for range scoops where the physical shelf order is already the desired result order.

**Recent condition-DX scoring:** `artifacts/condition-dx-score-report.md` scores the current condition shapes. Opened composite indexes expose direct condition syntax such as `personFullName.Where.KeyPart("firstName").AsString.EqualTo("John")` and `personFullName.Where.FullKey(" ").AsString.Contains("Smith J")`; raw descriptor construction through `LibraDexCompositePart.*` remains available for generated or low-level condition assembly.

**2026-06-02 restart handoff:** current composite condition public syntax is intentionally narrowed to two semantics only: explicit named part predicates through `personFullName.Where.KeyPart("firstName")...` and explicit whole-composite predicates through `personFullName.Where.FullKey()...` or `personFullName.Where.FullKey(" ")...`. `.AsComposite`, `Joined(...)`, `Joined*`, and `.AnyString` must not be revived as public or private condition-builder terminology. `.AnyString` was removed from the opened composite `.Where` surface, the raw `LibraDexCompositePart` helper surface, the internal pseudo-part sentinel, routed-composite executor state, harness proofs, and the condition-DX score report because it created a third composite-key selector concept outside the agreed `KeyPart` / `FullKey` model. Cross-part text search is now explicitly a `FullKey(...)` choice owned by the developer, while part-scoped text search is explicitly a `KeyPart(...)` choice. The current source tree has four tracked modified files from this slice: `LibraDexConditionBuilder.cs`, `LibraDexRoutedCompositeIndex.cs`, `LibraDex.Harness/Program.cs`, and this checklist. The ignored `artifacts/condition-dx-score-report.md` was also updated and should be consulted manually because normal `git status` does not show it.

**Recent retrieval/filtering proof closure:** the remaining non-mutation mapped proof rows are now deterministic materialization tests in `public-surface-api-sanity`: positive bookmark continuation, deferred index selector rematerialization, deferred structured-date selector rematerialization, named selector replacement with `WithIndex(...)`, caller-owned geohash and normalized-phone string codec examples, slash-delimited full-key composite wildcard matching, excluding-part full-key composite contains, currency-plus-minor-unit composite matching, and grouped bool-plus-created/updated `IsToday()` logic. `artifacts/condition-query-intent-proof.md` now leaves only the mutation-selection rows `211-215` at `Mapped`, so retrieval/filtering proof is closed enough to move into the mutate/delete lane without carrying known builder-shape gaps.

**Recent composite closure:** composite descriptors now have the first condition-executable routed-component proof through `LibraDexRoutedCompositeIndex`. `Where(...)` captures named part predicates as one condition leaf and materializes to a `CompositeMatch` primitive, so execution can walk tiered component routes such as `tenantId == A` then `username starts with J` without flattening parts into one concatenated key. The low-friction creation DX now supports lazy composite lifecycle builders from both `catalog.Indexes["group"]["name"].Composite<TIdentity>(...)` and `catalog.Indexes.Group("group").Composite<TIdentity>("name", ...)`, plus short aliases such as `C.Guid(...)`, `C.Text(...)`, `C.Unique`, and `Key.Of(...)`. Catalog metadata persists and reopens the ordered composite part contract, including part names, CLR types, key families, and projection flags. Composite contents now have durable DataKernel-backed routed node pages: each node stores one composite tier, terminal identities, and child component values with child page offsets. Inserts append immutable copies of only the changed terminal-to-root path and publish the new root offset through the fixed catalog slot, while untouched sibling branches keep their existing page offsets. In-memory child routes are maintained as ordered mini-router tables with binary-search lookup/update, avoiding linear sibling scans after node pages are loaded. Version 2 node pages now include a fixed-width child directory over separately encoded child values, and reopened composite indexes hydrate node pages lazily; exact composite lookup can binary-search a durable page for the next child offset without recursively loading every sibling branch. `CompositeMatch` traversal now also keeps unloaded nodes page-native for constrained tiers: ordinal equality uses the durable binary-search path, scalar/ordinal string `Between` lower-bounds into the child directory and stops after the upper bound, ordinal string `StartsWith` lower-bounds to the prefix and stops when the contiguous prefix region ends, and one-sided scalar/ordinal string bounds use lower-bound or start-of-directory scans with early stop. Part-scoped string `Contains`, `EndsWith`, and `MatchesPattern` now execute only through explicit `KeyPart(...)` semantics, while `FullKey().AsString` provides explicit whole-composite residual matching over encoded component bytes for all parts in index order with no delimiter by default. `FullKey(delimiter).AsString` inserts the developer-supplied delimiter as UTF-8 bytes. `Parts(...)` includes selected names while preserving index order and `Excluding(...)` omits selected names. Full-key string criteria are converted once to UTF-8 bytes, and typed full-key criteria such as GUID, binary, scalar, and date/time operands are encoded once into the same byte domain. Stored components remain in their key-domain byte encodings: string UTF-8, raw bytes as-is, GUID 16-byte value, and scalar/date values as sortable big-endian lanes. The composite permutation sweep still uses the existing `CompositeMatch` primitive; no additional data-retrieval primitive was required for named key-part pattern, full-key, selected/excluded full-key, or typed full-key operands.

**Next concrete slice:** retrieval/filtering is closed enough for the current composite condition surface. The mutate/delete lane now has two connected single-leaf condition-output bridges. `Delete().Execute()` runs when the backing index implements `IIdentityPrimitiveMutator`; routed composite indexes physically delete `All`, exact composite-key, and `CompositeMatch` matches with durable reopen coverage, all generic fixed scalar shapes (`SS8-8`, `SS16-8`, `SS8-16`, `SS16-16`, `FS32-8`, `FS32-16`) physically delete all/exact/range/boundary/membership/multirange condition primitives by rewriting only affected shelves, and the logical string `VS8` facade physically deletes exact string condition matches while maintaining exact, folded, sort-key, and reversed projection tuples by exact `(key, identity)` deletion. Scalar, composite, and logical string `SetKey(...).Execute()` now run when the backing index can capture primitive key/identity tuples and delete exact old tuples; they first materialize original tuples, ensure replacement tuples exist, then remove only exact old key/identity tuples so non-unique keys and replacement keys inside the original condition do not collapse into range-delete behavior. Direct scalar, composite, and logical string `Delete(key, identity)`, `Rekey(identity, oldKey, newKey)`, and scan-backed `Rekey(identity, newKey)` are connected through the same exact tuple primitive. `IIndex` now exposes non-generic `Delete` and `Rekey` mutation members with default capability failures for index families that have not connected exact tuple mutation yet. Composed condition mutation is explicit-target and low-ceremony through `DeleteFrom("indexName", ...)` and `SetKeyOn("indexName", ...)`: the composed condition selects identities, while the named target index is scanned and exact target tuples are mutated. Fixed scalar delete now marks removed slots with the named tombstone sentinel (`DeletedSlotOffset = 0`) and then normalizes ordinary public delete rewrites before staging, so persisted fixed shelves remain compact and the older reclaimed-offset ledger is no longer used by fixed scalar delete. Fixed and varlen shelf views expose the first executable metadata contract: `PhysicalItemCount`, `LiveItemCount`, `DeletedItemCount`, and, for varlen mutable shelves, payload used/live/deleted byte counts. Fixed shelf views now report non-zero deleted counts for tombstoned intermediate images, and fixed shelf durability batches retain dirty shelf byte images in session-local dictionaries until `CommitDurabilityBatch`, where they are normalized and flushed once. Full and partial fixed shelf rewrites both merge into those session-local dirty images during an active batch, keeping uncommitted fixed shelf bytes out of the `DataKernel` pending overlay. Pending fixed shelf reads normalize dirty images before writer-side reuse by default. Condition range-style deletes now use mark-only tombstone accumulation during active fixed-scalar batches for all six fixed scalar shapes, then commit-time normalization publishes compact shelf bytes. Each batch-local delete recomputes its target range against the pending writer shelf first, so repeated deletes against the same shelf accumulate instead of replacing earlier dirty state. Varlen mutable shelves (`VS8`, `VS16`, `VV`, `SV8`, `SV16`) now expose slot-level delete accounting: deleted slots are marked in runtime sidecars, live/deleted item counts update immediately, and `PayloadBytesDeleted` reports orphaned record bytes. `VS8`, `VS16`, `VV`, `SV8`, and `SV16` now have routed key-range delete primitives over those sidecars; all five also have exact tuple delete primitives, and scalar variable-identity deletes walk duplicate-key overflow chains. Publication normalizes the varlen slot stream back to live entries; `VS8` and `VS16` now also apply the first conservative payload-repack policy at publication, rebuilding the record arena only when orphaned payload is at least 4096 bytes and at least 25 percent of used payload bytes. Dirty var-key batch flushes evict stale read-shelf cache entries after publication. Cursor-local `LibraDexRangeReader<TKey,TIdentity>.DeleteCurrent()` and `SetKey(newKey)` are connected for every generic fixed scalar shape; delete mutates the retained shelf and backs up the cursor to the shifted survivor, while `SetKey` delegates the exact rekey to the owning index, treats the retained range as a traversal snapshot, invalidates current access, and lets the next cursor move skip the stale current row. The next mutate/delete work should promote additional condition-facing varlen logical facades onto these mechanical delete primitives, then decide whether varlen repack thresholds and empty overflow-chain cleanup need catalog/index-level options. Projection-backed acceleration for full-key or part-scoped text matching remains a later optimization lane, not a blocker for mutate/delete.

**Preserved DX direction:** the current adopted condition descriptor is not the final DX target. The next public-surface pass should review AbraxasDB's condition builder in depth and adapt/adopt as close to 100% of its condition-builder semantics as LibraDex can support. Important semantics to preserve include explicit grouping, reusable partially completed conditions, cloneable/composable condition fragments, deferred value expressions, deferred selector/index expressions, and final executable/materialized condition production only at time of need. Abraxas `PropPath` should map to a LibraDex index/projection selector inside an identity group, potentially deferred so a reusable condition can bind later to one of several indexes with the same or similar key domain. Keep same-index fluent composition distinct from cross-index composition: `.And`/`.Or`/`.Not` should continue the current index-local condition grammar, while `.AndAlso(...)` and `.OrElse(...)` should compose completed or partial conditions from other indexes in the same identity group. Opened index handles should expose low-friction typed condition entry points such as `age.Where.GreaterOrEqual(18)`, and identity groups should execute composed conditions with calls such as `people.GetIdentities(age.Where.GreaterOrEqual(18).AndAlso(status.Where.EqualTo(1)))`. Index creation/opening should prefer key-family names such as `Int32Keys<long>()` and `StringKeys<long>()`; `AsInt32`-style names belong to condition operand interpretation, not index factory shape selection. Public mutation should prefer `.Add(key, identity)` for ordinary append-like index insertion, with `.Insert` retained only if it remains useful as an alias or lower-level term. `slotIndex` should remain optional/advanced ceremony rather than something typical developers must care about during named index creation.

**Open decisions:**

1. What LibraDex name and object model should replace Abraxas `PropPath`: likely an index name or projection selector inside an identity group, not a literal object-property path.
2. How Abraxas index selectors map to durable LibraDex index descriptors, projection descriptors, composite key definitions, and identity-group metadata without importing SQLite SQL semantics.
3. Which Abraxas builder concepts transfer unchanged, which need LibraDex names, and which should be omitted because they imply unsupported or poor-performing execution.
4. How Abraxas deterministic-function behavior (`GV`, structured date/time, `SortKey`, folded text, GUID comparison/slicing, decimal ordered bytes, binary slicing, and set membership helpers) maps into LibraDex codecs, maintained projections, and execution plans.
5. Which remaining mutation-selection proof rows become the first executable checks after retrieval/filtering closure.
6. How grouped criteria and multi-key conditions compose only across indexes in the same identity group.
7. Whether varlen repack thresholds and empty overflow-chain cleanup should remain fixed policies or gain catalog/index-level options after more mutation/delete measurement.
8. The older physical-shape decisions from May 16 remain parked, but they are not the active lane until the adopted condition/index builder contract settles.

## 1. Mission

LibraDex is a custom, high-performance identity-index engine.

An identity index stores keys with identity values that point to data held elsewhere. The identity value is not the primary record. It may be a GUID, array index, file path, object handle, offset, or another external identity chosen by the caller.

The primary mission is low/no developer friction, where friction includes syntax, semantics, correctness, performance, efficiency, operational behavior, and restartability.

LibraDex should be file-backed, not only an in-memory concept. Its core read advantage is fast navigation to a sorted shelf of key/identity entries, followed by quickly scooping up a range of matching or adjacent identities with minimal per-entry interpretation.

## 2. Reference Model

**`.lbdx` file:** the default LibraDex index file. A single `.lbdx` file may hold multiple indexes.

**Index:** one complete searchable structure inside a `.lbdx` file. An index owns its root router, routes, shelves, metadata, and storage references for one key/value shape or access pattern.

**Catalog:** conceptual name for an index over one key shape or access pattern. Prefer `index` in code-facing names unless catalog language is clearer for the physical-library analogy.

**Key:** the ordered value used for lookup, seek, and range selection.

**Encoded key:** the stable byte representation used for sorting and routing. Routers operate over encoded key bytes.

**Key depth:** the current byte offset into an encoded key while routing.

**Prefix:** the byte sequence consumed while navigating from the root router toward a shelf.

**Identity:** a stable value that identifies other data held elsewhere. LibraDex stores and returns identities but does not own the external data they identify.

**Identity field:** the identity side of a shelf item. It is opaque to LibraDex except where the selected identity codec defines binary storage and equality behavior.

**Shelf:** a sorted physical/logical container of shelf items.

**Shelf item:** one key and identity-value tuple in a shelf.

**Shelf range:** the key range represented by a shelf.

**Shelf shape:** the physical shelf contract selected for an index profile. Shelf shape includes item layout, shelf extent size, slot/index strategy, search strategy, split policy, and mutability posture.

**Fixed scalar shelf:** a shelf shape for scalar encoded keys and scalar identity values using fixed-width fields and specialized byte math. The first fixed scalar shelf shape is `FixedScalarShelf16`.

**Fixed bytes shelf:** a shelf shape for fixed-width non-scalar encoded keys or identity values where comparison is byte-oriented rather than scalar-oriented.

**Variable-length shelf:** a shelf shape for variable-width keys, identities, or both. It may use a different payload/offset contract than fixed scalar shelves.

**Slot array:** the sorted indirection table inside a mutable shelf. In the first fixed scalar shelf, slots are `ushort` byte offsets to physical shelf items.

**Router:** a prefix-based navigation structure that routes keys toward another router or a shelf.

**1b-router:** a router that consumes one key byte at the current key depth.

**mb-router:** a router that consumes multiple consecutive key bytes at the current key depth.

**Root router:** the entrance router for a specific index. The initial root-router shape is a 1b-router.

**Route:** the combined mapping from a route prefix to the router or shelf to which it points.

**Route prefix:** the byte or byte sequence owned by a route at a specific key depth.

**Route target:** the structure referenced by a route, either another router or a shelf.

**Route slot:** the persisted route entry in the initial router format. A route slot is `10` bytes: `prefix-start-byte`, `prefix-end-byte`, and an `8` byte direct target file offset.

**Route range compression:** router behavior where one route slot can map a range of prefix byte values to the same target file offset, such as `0x0A-0x0F -> offset`.

**Expanded router:** a router whose route ranges have been refined as growth requires. A fully expanded 1b-router has `256` single-byte route slots, allowing direct index-style discovery while preserving the same persisted route-slot format.

**Scoop:** a mostly sequential range read after routing reaches the target shelf or shelf span.

**Normal shelf split:** a shelf split where the owning router can still represent the new route. Some percentage of the original shelf remains in the original shelf, the remainder moves to one new shelf, and the incoming item lands in the shelf that owns its sorted position.

**Transmorphic shelf split:** a shelf split where the owning router is full. The owning router is not dirtied for expansion; instead, the shelf's existing storage location is rewritten as a child router, and the old shelf data plus incoming item are redistributed into two shelves.

**DataKernel:** LibraDex's low-level data movement and durability core. It owns storage-unit policy, buffer ownership, file-offset mapping, dirty/new tracking, sequential write staging, commit shaping, and durable publication.

`DataKernel` is the only layer that should know whether the current backing store is durable file storage or volatile RAM. Shelf, router, and index layers operate through offsets, staged byte reservations, reads, and commits; they should not branch on disk-versus-memory behavior.

**Page manager:** analogy term for the `DataKernel`. LibraDex uses page-manager-like ideas but does not limit the `DataKernel` to one universal page size or classic B-tree page semantics.

**Storage unit:** a `DataKernel`-owned file-backed unit of storage. Storage units may have different configured classes rather than one universal size.

**Storage class:** a configured storage-unit category, such as small router pages, larger shelf extents, metadata/header pages, or future overflow units.

**Dirty page:** a `DataKernel`-owned page whose in-memory contents differ from the durable file state.

**Commit:** a `DataKernel` operation that publishes dirty page changes, newly staged data, and durable metadata changes to the file/disk boundary.

**Commit batch:** a group of dirty or newly allocated storage units published together.

**Superblock:** the fixed file-start structure at offset `0`. It identifies the `.lbdx` file, records global format metadata, and provides or points to the index-of-indexes needed to find each index root router.

**Index directory:** the index-of-indexes. It records the offsets where root routers for indexes start, plus the metadata needed to identify each index.

**Manifest/header:** durable metadata that lets a `.lbdx` file reopen and find indexes, roots, format version, page layout, and codec/profile information. The superblock is the file-level header.

**File offset `0`:** reserved for the superblock and invalid as a route target. Offset `0` may be used as a null/unused route-target sentinel.

**Page/block/segment:** file-backed storage units used to persist routes, shelves, metadata, and future mutation state.

**Codec:** the component responsible for stable binary representation, comparison, and round-tripping of keys or identities.

**Condition builder:** the adopted public grammar for data selection and condition-scoped operations. The target source model is AbraxasDB's builder chain (`Where` -> selector -> value type -> operator -> grouping/continuation/end), modified for LibraDex's identity-index model and encoded-key execution.

**Index selector:** the adopted public grammar for declaring or selecting an indexed key/projection. In LibraDex, an Abraxas-style selector must resolve to an identity-group index, maintained projection, or composite index descriptor, not to ad hoc object inspection at query time.

**Projection index:** a maintained alternate encoded key for a logical value, such as folded text, sort-key bytes, structured date/time, GUID segment/text forms, or another codec-backed representation. Projection indexes are explicit metadata and storage choices, not hidden query-time transformations.

**Identity group:** a declared set of indexes that share one identity universe. Grouped or multi-key conditions may compose identities only across compatible indexes in the same identity group.

**Round-trip type:** a developer-facing .NET type whose value can be serialized to bytes and reconstructed. Round-tripping alone is not enough to make a type an efficient LibraDex key; indexed key support also needs explicit ordering, equality, projection, and codec behavior.

## 3. Non-Goals

LibraDex is not a full key-value store.

LibraDex is not a relational database engine.

LibraDex is not a document store.

LibraDex is not initially optimized for arbitrary predicate evaluation. The primary optimized operation is ordered lookup/range access over a catalog.

LibraDex should not hide expensive behavior behind convenient APIs. Developer friction is reduced by making the fast path natural and the expensive path visible.

LibraDex should not make the temporary LibraDex criteria/builder names canonical. They are scaffold terminology until replaced by the adopted Abraxas condition/index builder shape.

LibraDex should not imply that every Inheto/Abraxas round-trip type is automatically an ordered, indexed, or projection-ready key type. Unsupported or scan-required conditions must remain visible until a codec/projection/index plan exists.

## 4. Core Invariants

Shelf entries are ordered by the catalog key comparer.

Key comparison must be stable across process restarts, machines, and file reopen operations for a given catalog format.

Identity values are opaque to LibraDex except where a selected identity codec defines binary storage and equality behavior.

Persisted scalar numeric fields must use a canonical sortable encoding. Native machine endianness must never be treated as the persisted sort layout.

File-backed data must have an explicit compatibility story before format changes are treated as durable.

File offset `0` is reserved for the superblock and must never be a valid router target.

Range reads should minimize random I/O after routing has reached the relevant shelf span.

Shelf growth should prefer local route refinement over B-tree-style upward split propagation.

When a normal shelf split occurs, the expected structural writes are the original shelf, one new shelf, and the owning router.

When a transmorphic shelf split occurs, the owning full router should not be dirtied. The former shelf location should be reused as the new child router, and two shelves should receive the redistributed data.

Router route slots use direct file offsets. The initial persisted route-slot format is `10` bytes: start byte, end byte, and `8` byte target file offset.

Design choices should be checked against the physical-library model only where the analogy improves clarity. The implementation must be justified by concrete data layout, I/O behavior, and algorithmic cost.

Design choices should not be imported just because another index, database, or tree-like structure has a similar smell. The default reasoning path is to discard borrowed solution templates, inspect the low-level operations available, and compose the cheapest correct sequence of byte movement, routing, caching, write combining, and file-growth behavior for the current concern.

Raw `DataKernel` performance baselines are the comparison anchor. Structural metrics such as route depth, read-call count, contiguous runs, split count, and file slack explain distance from raw throughput; they do not by themselves define failure or success.

Progression checks should lead with correctness, logical throughput relative to raw baselines, and file growth. Counts such as reads per range, writes per batch, shelf count, route depth, contiguous runs, and bytes moved are causal diagnostics; they become decision drivers only when tied to measured drift away from raw baseline behavior or unacceptable file growth.

Benchmark reports should include a compact percent-only summary in addition to detailed metrics. The detailed table should keep logical throughput, byte movement, syscall counts, and file-growth values together; the percent summary should make raw-baseline distance and previous-checkpoint drift visible without requiring wide-table scanning.

Timing-sensitive benchmark commands should support repeated samples and report a median row when practical. Single timing samples are acceptable for quick iteration, but progression claims should prefer median-of-repeat evidence so transient host noise does not drive design decisions.

Uncertain implementation paths should be isolated when practical. Prefer an experimental partial class file, such as `LibraDexFileSession.Experimental.RangeReadPlan.cs`, for candidate storage or routing strategies that may be reverted after measurement. Keep the stable call-site hook small, measure the candidate against raw-baseline distance and file growth, then either remove the partial file or fold the winning path back into the main implementation.

The distinction between scalar, fixed, and variable-length shapes is not only descriptive. It determines how values are encoded, how ordering is preserved, where compare cost is paid, and how concrete the hot-path byte views can remain.

## 6. Implementation Invariants

LibraDex targets `.NET 8`.

The implementation should use low-level .NET primitives where they materially improve performance, allocation behavior, or file-backed data access clarity. Expected primitives include `Span<T>`, `ReadOnlySpan<T>`, `Memory<T>`, `ReadOnlyMemory<T>`, `MemoryMarshal`, `Unsafe`, `Marshal`, and targeted P/Invoke where the platform behavior is known or deliberately being tested.

`RandomAccess` is the initial preferred file I/O primitive for positional reads and writes.

The implementation should be low-allocation and low-heap by default. Prefer views, projections, slices, stack-local state, pooled buffers, and `ref struct` shapes where they keep the hot path explicit and safe enough to reason about.

The `DataKernel` is the fulcrum of the design. It should own the relationship between memory buffers, file offsets, dirty state, newly staged data, and durable commits so that routers, shelves, and indexes can remain focused on their own formats and operations.

The initial `DataKernel` backing strategy is cache-first with pooled managed buffers. Unmanaged memory and memory-mapped files are reserved for later last-mile optimization if evidence shows they are needed.

The `DataKernel` manages configurable storage classes rather than a single hard-coded page size. Router storage should favor small pages, shelf storage should favor larger sequential extents for scoop efficiency, and metadata storage should favor predictable reopen behavior.

The `DataKernel` should support both file-backed and RAM-only backing modes. RAM-only mode preserves raw offset, append, read, commit, and telemetry semantics, but it is temporary and not durable. Shelf, router, and index byte formats should not branch on backing mode.

Use four implementation classifications when bringing up new concrete shapes:

- **DataKernel:** shape-agnostic byte movement, staged reservations, fixed-offset rewrites, reads, commit coalescing, durability, and telemetry. Keep it mostly static across new shapes. Change it only when a concrete substrate need is proven, not because a new shelf shape exists.
- **Router:** shape-agnostic route-page semantics, direct-index route slots, route targets, key-depth metadata, arena metadata, and router read caches. Routers operate on encoded prefix bytes and offsets; they should not know tuple width, identity width, or shape-specific comparison rules.
- **Shape/Shelf:** concrete and intentionally duplicable. Each shape owns its byte layout, tuple ordering, prefix extraction over its encoded key, slot/item math, insertion mechanics, split/transform mechanics, and hot-path mutation choices. Duplication is acceptable when it preserves predictable performance and prevents one shape from perturbing another.
- **Harness:** concrete and intentionally duplicable. Each shape should get its own proof ladder while using established shapes, especially `SS8-8`, as regression anchors. Harness duplication is preferable to a generic test layer that hides shape-specific evidence or weakens telemetry checks.

Defer consolidation until multiple concrete shapes are complete and measured. Consolidate only where repeated code is mechanically identical, clearly non-hot, or demonstrably harmless to low/no developer friction and performance control.

Values that act as knobs or levers must not be hard-coded into hot-path logic. Defaults are acceptable, but page size, shelf extent size, allocation growth, commit thresholds, pooling sizes, and related policy values should be named and configurable through internal policy objects or equivalent structures.

Hot paths should avoid avoidable call-chain depth. Delegates, callbacks, visitor patterns, LINQ, virtual dispatch, and convenience abstractions belong at outer ergonomic layers unless a measured case justifies them inside page, shelf, router, or commit paths.

Hot loops should avoid repeated property/field access when a value is used more than once. Prefer copying frequently used fields, properties, array/list references, lengths, and options into locals near the loop when it improves generated code clarity or reduces repeated dereference/register pressure.

Hot-path APIs should be shaped for likely JIT and NativeAOT inlining. Tiny byte-projection, route-slot, offset-computation, bounds, and layout helpers should stay small, non-virtual, allocation-free, and free of logging or formatting. Use `AggressiveInlining` selectively for proven hot helpers rather than broadly decorating the codebase.

Dirty state should be structural. Shelf, router, superblock, index-directory, or `DataKernel` write operations should make dirtiness inherent to the mutation path rather than relying on separate caller-managed `MarkDirty`-style steps.

New data should be staged into large sequential buffers where possible so commits can publish it with one large positional write or a small number of long sequential writes. Existing dirty storage units should be sorted and coalesced by file offset where useful.

Commit behavior is performance-oriented as well as durability-oriented. Syscall count, written bytes, dirty unit count, coalesced range count, and flush count should be visible in commit telemetry from early development.

Commit design must balance syscall count against file-size growth and future compaction tax. Sequential new-data writes are valuable, but transmorphic shelf splits should reuse the old shelf location for the new child router to avoid abandoning a live extent and forcing cleanup later.

File-backed raw commits should avoid `SetLength` by default. Positional writes beyond the current end of file can grow the file naturally; explicit preallocation or length-setting should be a named policy only when deliberately benchmarked.

Low-level code must still preserve developer friction goals. Unsafe or interop-heavy paths should be isolated behind small, well-named APIs with clear invariants rather than leaking complexity through the public surface.

Development should be agile and incremental, not storage-internals TDD-first. Early storage work should favor small reversible slices, direct validation harnesses, and undo-then-apply patterns. Public builder adoption is different: use a TDD-like permutation-first pass to describe condition/index builder scenarios before bridge code, then implement only the repeated, measured execution patterns those scenarios prove necessary.

Performance and data-file tests should write test data to the `T:` drive. That SSD is dedicated to this project and avoids unrelated disk activity contaminating measurements.

Performance reports should include both logical-throughput and byte-throughput metrics. For writes, headline `items/sec` and `us/item`; also report `MiB/s`, `bytes/item`, `writes/batch`, and `commits/batch`. For reads, headline `identities/sec` or `ns/identity`; also report `MiB/s`, `bytes/identity`, and `reads/range`. Use item/identity throughput to judge LibraDex usefulness, and byte throughput to diagnose whether `DataKernel` and storage movement are efficient.

## 7. DataKernel Design Position

The LibraDex `DataKernel` is closest to a focused hybrid of a database buffer manager, B-tree page cache, SSTable-style sequential writer, and copy-on-write-friendly publication layer.

It intentionally borrows known storage-engine concepts: page identity, buffer ownership, dirty tracking, positional file I/O, commit batches, and durable metadata publication.

It intentionally does not start as a one-size-fits-all database buffer pool. LibraDex can optimize around identity-index routing and range scoop behavior, use different storage classes for routers and shelves, make sequential construction a first-class path, and keep hot-path abstractions shallow.

## 8. Byte Layout And View Pattern

LibraDex should use a tiered pattern for code that lays over bytes owned by the `DataKernel`.

Tier 0: layout helpers.

- Static classes or readonly structs.
- Constants for offsets, sizes, masks, flags, and format versions.
- Tiny read/write helpers over `Span<byte>` and `ReadOnlySpan<byte>`.
- No allocation, ownership, virtual dispatch, logging, or formatting.
- Shaped for likely inlining.

Tier 1: hot byte views.

- `ref struct` readers/writers over `Span<byte>` or `ReadOnlySpan<byte>`.
- Used by shelf, router, superblock, and index-directory hot paths.
- No interfaces, boxing, async, delegates, or heap ownership.
- May duplicate convenience logic from outer layers when that keeps byte paths shallow and fast.

Tier 2: outer models and ergonomic APIs.

- Normal structs, records, or classes where useful.
- Used for public APIs, diagnostics, harnesses, metadata descriptions, validation output, and configuration.
- May allocate, format, log, and expose friendly names when not on the hot path.
- May duplicate fields or logic from byte views because the purpose is different.

Do not make hot byte views pay for outer-layer convenience. Do not make outer APIs unpleasant just because hot-path views are constrained. Intentional duplication between tiers is acceptable when it protects both performance and low/no developer friction.

## 9. Encoded Key Routing Rules

Routers operate on encoded key bytes, not developer-facing key objects.

Hot routing APIs should consume `ReadOnlySpan<byte>` for encoded keys. The routing path should access prefix bytes by integer index, such as `encodedKey[keyDepth]`, rather than by object comparison, string operations, slicing, or codec dispatch at each router level.

Key encoding should happen before routing:

- Outer ergonomic APIs may accept `string`, `Guid`, numeric values, or other developer-facing key types.
- The selected key codec encodes that key once per operation, or once per batch item in a shared workspace.
- The router path receives the encoded bytes and should not allocate, normalize, or compare developer-facing key objects.
- Codec dispatch should be resolved before entering the router loop. Avoid virtual/interface codec calls per router level.

Hot routing rules:

- Prefer `ReadOnlySpan<byte>` for encoded keys in immediate routing calls.
- Use `ReadOnlyMemory<byte>` or pooled buffers only when the encoded key must outlive the stack/local operation.
- Avoid repeated slicing in router loops; carry `keyDepth` and index directly.
- Copy reused key length, router-page references, route counts, and flags into locals near hot loops.
- Too-short keys should return no route or a defined terminal result; they should not throw in the hot routing path.
- Routers inspect only prefix bytes. Full key ordering and equality belong to shelf search and key codec comparison rules.

Batch and high-level APIs should preserve low/no developer friction without changing the hot path:

- Batch routing should accept already-encoded keys where possible.
- Batch encoding should reuse stack or pooled workspaces to avoid per-key heap allocation.
- Fixed-size codecs should expose direct byte writes or views suitable for stack/local buffers.
- Variable-size codecs should encode once, then route over the resulting byte span.

These rules are intended to protect router performance. A fast router page format can still lose to avoidable key encoding, allocation, slicing, or per-level codec dispatch.

Public APIs should route developer-facing key and identity types to concrete physical shapes rather than asking normal callers to choose shape names directly:

- Developer-facing methods may be generic, for example over `TKey` and `TIdentity`, when that reduces syntax and semantic friction.
- The public factory/router layer should map common logical types to optimized physical shapes, such as scalar 8-byte key/identity data to `SS8-8` and 16-byte key with 8-byte identity data to `SS16-8`.
- Concrete shape names are storage, diagnostics, benchmarking, and explicit-override terms. They should not leak into ordinary public call sites unless the caller deliberately asks for physical-shape control.
- Shape-specific shelves remain free to duplicate hot code and tune layout for common persisted key/identity widths even when the public API looks generic.
- The public type router must preserve explicit backing and create/open semantics; low-friction type routing should not hide durability or file-open behavior.

Public API surface review should use these categories so naming and DX decisions are not mixed together too early:

1. Construction / opening: creating a `.lbdx`, opening an existing file, creating or opening an index, selecting a backing mode, and deciding whether the caller is working with a whole file/group or one index.
2. Configuration: choosing physical shape/profile, codec behavior, maximum key/identity lengths, duplicate policy defaults, optimizer policy, and other options that change semantics or performance.
3. Discovery / metadata: listing indexes in a file, checking whether an index exists, reading shape/profile metadata, and validating compatibility before opening.
4. Selection / conditions / retrieval: expressing Abraxas-adopted condition builder chains over identity-group indexes, resolving those conditions to known index descriptors or maintained projections, and executing the cheapest correct identity selection path.
5. Navigation / readers: cursor-style traversal, seek/skip/count behavior, row-local spans, and datareader-style APIs that avoid disconnected materialization.
6. Materialization / result ownership: caller-owned spans, disconnected pooled buffers, arrays, flat payload views, copy helpers, and lifetime rules for results that outlive a reader operation.
7. Insert / delete / mutation: single inserts, duplicate handling, delete/update semantics, and any mutation API that changes shelf or route contents.
8. Batching / durability: grouped mutations, commit/abort behavior, durability boundaries, write telemetry, and batch-oriented low-allocation paths.
9. Maintenance / optimization: route optimization, shelf repacking, cache policy, background or explicit maintenance, and production-safe tuning controls.
10. Stats / diagnostics / observability: passive catalog/index stats, trip-counter markers, telemetry snapshots, route/shelf stats, file growth, compatibility reports, validation helpers, and benchmark-facing introspection.
11. Disposal / lifetime: ownership of sessions, indexes, readers, batches, and disconnected buffers, including what remains valid after each object is disposed.
12. Tools / utilities: import/export helpers, format inspection, repair tools, test harness helpers, and developer utilities that are not normal hot-path APIs.
13. Compatibility / migration: file format versioning, profile evolution, upgrade checks, and explicit migration or repair flows.

Adopted condition and index builder direction:

- Use AbraxasDB's condition builders and index builders as the copy-then-modify source, not the temporary LibraDex criteria-builder style.
- Treat Abraxas `PropPath` as a source concept that likely distills to LibraDex index name, projection selector, or composite part inside an identity group. Do not preserve property-path terminology unless the adopted API proves it has a low-friction LibraDex meaning.
- Review Abraxas connection-manager deterministic functions before finalizing LibraDex codecs and projections. `GV`, structured date/time packing, sort keys, folded text, GUID helpers, decimal ordered bytes, binary slicing, and set helpers are evidence for projection semantics, not SQLite dependencies to import directly.
- Preserve the Abraxas builder strengths that matter for LibraDex: typed value selection, grouped criteria, continuation/end grammar, multi-key usage, and index selector variants.
- Start from condition permutations instead of method-name debates. For each condition scenario, decide whether it can use an existing index/projection, requires a maintained projection or composite index, degrades to a visible scan-like path, or should be rejected until supported.
- Inserts do not need the condition builder. Public insert methods should remain simpler facades over internal primitives with conveniences for supported .NET types that can round-trip through bytes and have explicit codec support.

Construction / opening decisions:

- The catalog should be the first public construction concept. In public API discussion, `catalog` describes a grouping of indexes, while `index` describes one searchable structure inside that grouping.
- The preferred public catalog construction call shape is `Catalog.Create(...)`, `Catalog.Open(...)`, and `Catalog.CreateOrOpen(...)` from the `LibraDex` namespace. This keeps the common call site short after `using LibraDex;` while leaving room for other namespace-level types.
- Creating or opening a catalog should make backing explicit and should support both memory-only and file-backed modes.
- The initial catalog factory pattern should be `Catalog.Create(path)`, `Catalog.Open(path)`, `Catalog.CreateOrOpen(path)`, and `Catalog.CreateMemory()`, each with an optional `CatalogOptions` parameter.
- `CatalogOptions` should start as an empty public options type. Add members only when the surrounding API surface proves a concrete need, rather than pre-filling placeholders that may constrain later naming or policy choices.
- The catalog factories should return the concrete public `Catalog` type. `Catalog` should own its static factory methods rather than returning a differently named `LibraDexCatalog` wrapper or an interface in the first public surface.
- `Catalog` should be disposable. `Dispose()` should release/close the underlying memory or file-backed session, and the public surface may also expose an explicit close-style method that delegates to the same lifecycle path for callers who prefer verb-based shutdown over `using`.
- Individual index construction should hang under an identity group, not directly under ungrouped `catalog.Indexes` factories. The preferred short call-site shape is `catalog.Indexes.Group("people")...`, with `catalog.Indexes["people"]` as shorthand for the same identity-group scope. `IdentityGroup` can remain a precise type/documentation term, but member names should prefer `Group` when the surrounding `Indexes` context already supplies meaning.
- `Group` / `IdentityGroup` is the chosen public concept. Avoid `IdentitySource` because source implies storage origin, provider, feed, or ownership, while LibraDex only needs to know that a set of indexes shares one identity universe for composition.
- Identity group names must be unique within a catalog's identity-group namespace. Index names should be unique within an identity group; global uniqueness across all groups can remain a diagnostics/policy question unless implementation proves a need.
- Every normal public index factory should live under an identity group before release. Ungrouped root factory syntax was scaffold-only and should be removed rather than preserved as a legacy surface because LibraDex is pre-release.
- Identity group metadata should be persisted and exposed through discovery APIs, for example `CatalogIndexInfo.Group`, `catalog.Indexes.Groups()`, and `catalog.Indexes["people"].List()`.
- Identity groups are developer-declared compatibility metadata, not object-schema enforcement. LibraDex can validate that multi-criteria composition uses indexes from the same group, but it cannot prove the developer's object store semantics unless higher layers provide more metadata later.
- Index factories should also accept an optional options object. Start with an empty public `IndexOptions`-style type and add members only as concrete API needs appear; shape/profile, duplicate policy, and optimizer defaults are likely candidates, but should not be precommitted before the public surface proves the right names and ownership level.
- Options inheritance should be explicit and shallow: library defaults feed catalog-level defaults, and catalog-level index defaults feed per-index options. `CatalogOptions` may later expose catalog-owned settings plus `DefaultIndexOptions`; per-index options override only index-relevant values. Resolve effective options at index create/open time rather than depending on mutable ambient defaults.
- Index instances should be disposable and should expose an explicit `Close()` method that delegates to the same lifecycle path as `Dispose()`, matching the catalog lifetime pattern.
- `Create`, `Open`, and `CreateOrOpen` should remain the standard public verbs for construction/opening. Convenience aliases should not replace those explicit semantics.
- Shape-specific index factories should not be the active construction-design focus until the catalog-first API shape is settled.
- Identity-group batching should exist in addition to index-level batching. `group.Batch` is the preferred multi-index object-ingest DX and should supersede any batch setting on a specific index while that group batch is active. Keep `BatchManager` as an implementation/type concept if helpful, but the public member should be the shorter `Batch`.
- Index-level batching should remain for single-index or low-level workloads. Group-level batching should coordinate writes across all indexes in that identity group without making batch mode a SQL-style transaction or rollback boundary.

Selection / condition / retrieval scaffold captured 2026-05-18, superseded 2026-05-20:

The May 18 notes below are historical scaffold evidence, not the current naming or builder contract. Do not use their operator names, terminal names, or direct criteria object model as design anchors. The current direction is the Abraxas copy-then-modify condition/index builder adoption described in section 0 and the adopted builder direction above.

- Per-call duplicate-key policy should not remain on the public `Insert` signature. Uniqueness is an index-level contract chosen at create/open time through `IndexKeys.Unique` or `IndexKeys.NonUnique`; root insert calls should not accept `allowDuplicateKeys`.
- The first query surface should focus on single-index retrieval. Multi-index `AND`/`OR` planning can be designed later after one-index criteria, result ownership, and execution metadata are stable.
- Multi-index `AND`/`OR` should be described as multi-criteria identity composition. For a catalog identity group such as `people`, indexes like first name, last name, birth date, age, and gender are analogous to separate indexes over one identity universe; combining them narrows or expands identity results from the same source of identities.
- Normal multi-criteria lookup must stay inside one `IdentityGroup` unless caller code deliberately orchestrates broader work. Mixed-identity-group composition is caller-owned and should remain explicit because the caller knows whether identity values share meaning, whether operations can run in parallel, and what result metadata is needed.
- Multi-criteria composition should validate that participating indexes belong to the same identity group unless the caller uses a deliberate advanced override. The default returned shape should favor identities because keys from multiple indexes do not form one coherent key shape.
- LibraDex needs one public selection contract: the adopted Abraxas-style condition builder. Handwritten code and generated/programmatic callers should both target condition descriptors first; root index handles should expose insert, primitive reader, maintenance, stats, and metadata surfaces, not a parallel direct retrieval grammar.
- Abraxas-style condition translation targets an internal identity-primitive spine after condition materialization. That object model is execution plumbing behind adopted conditions, not a second public query language.
- The non-generic `IIndex.Criteria` builder has been removed. Adopted conditions validate runtime key values and prepared-set key types when they materialize against opened indexes, preserve operands for classification/bridge planning, and then create immutable identity-criteria leaves through the primitive request spine.
- Programmatic selection composition is identity-group scoped and should be expressed through adopted condition descriptors. Internal composition may still use `And`, `Or`, `Except`, and `Not`, but those members are not a public API target.
- Condition nodes should preserve the chosen index name, adopted operator, typed key values, projection requirements, and deferred value shape where useful. This maps to Abraxas' existing condition concepts without restoring the deleted LibraDex-only fluent criteria builder.
- Multi-criteria result shaping is identity-first. Adopted condition terminals record identity ordering, duplicate-identity handling, skip/take, and bookmark options. The default is natural plan order with distinct identities because a composed condition may span several indexes with no coherent shared key order.
- Identity ordering and duplicate policy are explicit descriptor choices. `IdentityResultOrdering.PlanNatural`, `.IdentityAscending`, and `.IdentityDescending` describe output order, while `IdentityDeduplication.Preserve` versus `.Distinct` describes whether repeated identities from overlapping criteria are meaningful. Physical execution should honor these options or reject unsupported combinations rather than silently sorting/materializing.
- Adopted condition planning now returns the first physical-planning descriptor for multi-criteria identity retrieval. It classifies `SingleIndex`, `Intersection`, `Union`, `Difference`, `Complement`, and composite trees; records leaf count, depth, participating indexes, negation presence, ordering/paging/distinct requirements, and expected materialization class (`None`, `StreamingMerge`, or `IdentitySet`). It does not materialize identities yet.
- Planner defaults are intentionally conservative: single-index preserve projections can be stream-only, intersections/differences can be streaming-merge candidates, unions and complements require identity-set state, and explicit ordering/paging/distinct options force identity-set materialization until ordered identity-stream execution is connected.
- Adopted condition terminals now provide the first connected multi-criteria identity execution path for supported leaves. They can materialize identity results for `All`, equality, two-boundary comparisons, boundary criteria, membership, and condition-derived multi-ranges over executable generic indexes, then compose them internally while applying de-duplication, identity ordering, skip, take, and bookmark-position shaping. Text-like and pattern-like operators now route through declared maintained projections when available, or through the explicit `StringPattern` primitive over compact exact string index keys when a scan-backed fallback is the best available bridge.
- `LibraDexConditionEndCondition.Get(...)` returns `LibraDexIdentityExecutionResult`, pairing materialized identity objects with the selected plan and result diagnostics. Negative bookmark positions are rejected during projection option validation rather than being treated as ordinary skip math.
- `LibraDexConditionEndCondition.ToList<TIdentity>(...)` provides a typed materialization helper over the adopted condition executor. It validates every runtime identity against the requested CLR type so adapters that know the identity type at their boundary do not need to hand-roll object casts.
- `LibraDexCondition.ForGroup(group)` is the adopted Abraxas-style condition builder. It records index-name leaves, classifies each leaf before execution, and binds against an index resolver through condition terminals. The older `LibraDexIdentityConditions` helper and `LibraDexIdentityCondition` compatibility builder have been deleted so they cannot leak back into design or tests.
- `LibraDexConditionEndCondition` now owns the first adopted terminal helpers: `IDs`, `IDsWith`, `Plan`, `Get`, `Iterate`, typed `ToList<TIdentity>`, `Exists`, and `Count` against an index-name resolver. New selection tests should use these terminals instead of materializing `IIdentityCriterion` directly unless the test is specifically about the internal execution bridge.
- `LibraDexConditionEndCondition.Groups(resolveIndex).By(index)` is the adopted condition-scoped grouping bridge. It lets new grouping call sites stay on the adopted builder while the grouping index supplies the key axis and the condition resolver supplies candidate identities.
- The pre-adoption condition-builder terminals are gone. New tests must use `LibraDexConditionEndCondition` terminals directly.
- Condition execution diagnostics now count candidate identities scanned across the composed criteria tree rather than only the final materialized result length. For example, an intersection that scans two two-row leaf streams and returns one paged identity reports `RowsScanned == 4` and `RowsReturned == 1`, which is more useful for future cost planning and code review.
- Internal criterion projection helpers remain execution plumbing. Adopted-builder callers should prefer `LibraDexConditionEndCondition.Iterate(...)` and typed `ToList<TIdentity>(...)`.
- Plan-natural negated iteration now asks the first executable leaf for its internal identity universe, then excludes the child result set. Grouped catalog indexes stream a de-duplicated union of `All` identities across indexes in the same identity group; ungrouped handles fall back to the first leaf's own `All` primitive. This gives `Not(...)` a real catalog-backed group universe without exposing a public identity-source abstraction yet.
- Text-like and pattern-like condition operators are classified as projection-backed or visible-scan-like requirements before execution. Projection-backed routes use maintained folded, sort-key, reversed folded, or reversed exact subindexes; scan-backed routes use the explicit `StringPattern` primitive, which can narrow exact-key candidate ranges for equality, membership, starts-with, and leading-literal wildcard cases before applying .NET residual text comparison.
- The old direct index retrieval facade has been purged from the codebase. Root index handles no longer construct or expose `index.Find(...)`, `index.Between(...)`, `index.Prefix(...)`, `index.Keys`, `index.IDs`, `index.Not`, `index.Aggregates`, `index.Grouped`, `index.Prepare`, positional/rank facades, or their query/projection descriptor classes.
- Tuple/query/projection descriptor classes that supported the prior direct API have been deleted. Remaining read paths are low-level range readers, all-tuple iteration used by condition grouping, and identity primitive execution used by materialized conditions.
- Set composition belongs to the condition tree through `And`, `Or`, and `Except`, not through direct query-object set combinators. This matches the Abraxas condition-builder model and avoids making generated callers choose between two equivalent public query architectures.
- Result shaping is adopted-condition-terminal. Identity materialization, streaming, existence, counts, grouping, ordering, de-duplication, skip/take, and bookmark handling should hang from `LibraDexConditionEndCondition`, not from root index retrieval verbs.
- Aggregate and positional retrieval concepts should be reintroduced only as condition-terminal operations when their semantics are settled. They should not revive `index.Aggregates.Count.Between(...)`, `index.Middle.Between(...)`, or similar direct retrieval grammar.
- The deleted compatibility builder should not be recreated to recover parameter replacement, mutation, or object-model composition coverage. Needed features should be added as adopted condition descriptor/terminal behavior only after condition permutations prove the bridge shape.
- Internal leaf execution has been rebased onto `LibraDexIdentityPrimitiveRequest`, a normalized private primitive request over `LibraDexCriteriaKind` plus materialized operands. The private executor is the bridge from adopted condition intent to physical `get`/`set`/`delete` primitives. The primitive executor exposes both materialized and iterator forms so plan-natural condition retrieval can stream leaf identities through range readers instead of building a leaf list first.
- Ordered negated point and range conditions now bridge to the union of the lower and upper ordered extents. This includes generic `NotEqualTo`/`NotBetween` and structured date `YearNotEqual`/`YearNotRange`, avoiding full identity-universe complement materialization for cases where the encoded key order already describes the exclusion.
- The old internal leaf-executor fallback has been removed. Condition execution now requires an `IIdentityPrimitiveExecutor`, keeping one internal read spine behind the condition builder.
- Adopted condition materialization creates identity leaves directly from primitive intent diagnostics instead of calling older direct index-retrieval facade methods. This keeps condition construction independent from compatibility lookup adapters.
- Adopted condition materialization must still validate runtime key values and prepared-set key types against the opened index metadata. The condition-builder path is independent from the removed direct lookup methods, but it should remain just as strict about key type mismatches.
- Late-bound and replaced condition operands are validated when the condition materializes. This preserves Abraxas-style deferred parameter behavior without letting bad runtime values bypass index key contracts.
- The range term should be `Between`, not `Range`, because it matches developer expectation from Abraxas/SQL-style condition builders while still describing ordered-key retrieval clearly.
- Older direct query-intent methods on index facades are no longer part of the public surface. Do not add new public retrieval verbs directly to index handles; the condition builder and shape/index builders carry the canonical public/programmatic API.
- XML comments and result/query metadata should explain whether a method is normally fast-path, projection-backed, or scan-backed. The caller should express intent once and LibraDex should choose or report the execution strategy.
- Do not promote the May 18 criteria-name list into the current design. Rebuild the supported condition vocabulary from the adopted Abraxas builders, then map each scenario to index-backed, projection-backed, composite-backed, visible scan-like, or unsupported execution.
- Existence should be a condition-terminal shortcut because it communicates no materialization and can stop at the first match. Use `condition.Exists(...)` or an equivalent criterion projection path rather than reintroducing `index.Exists(...)`, `index.ExistsIn(...)`, or `index.ExistsInSet(...)`.
- Negation should be exposed through the condition builder, for example `Where(index).Not.Find(key)`, `Where(index).Not.Between(a, b)`, and grouped `NotGrouped(...)`. Internally these can route to the same criteria objects with a negation flag.
- Do not use an optional enum parameter for negation on every method. Examples such as `Where(index).Contains(value, Match.Exclude)` read poorly and weaken positive-call DX.
- `Not.Find(key)` is valuable and should not be rejected as broad-scan-only. In duplicate-key, low-cardinality indexes such as boolean or enum keys, it represents a practical complement retrieval over ordered key runs.
- Ordered duplicate-key retrieval should use key-run scooping. `Find(key)` should seek to the first matching key-run extent and stream/scoop contiguous identities until the key changes, rather than evaluating every row.
- Negated equality should use complement key-run scooping. `Not.Find(key)` should plan as key-space slices before and after the excluded key-run, not as row-by-row `key != value` filtering.
- The same complement planning applies to `Not.Between(a, b)`, `Not.Prefix(p)`, and sorted/prepared `Not.InSet(set)` where the key space can be expressed as ordered included and excluded runs.
- Low-cardinality duplicate-key indexes are a potential LibraDex advantage over SQL/B-tree systems. Boolean or enum indexes can be useful because equality and negated equality can exploit ordered runs and dense shelf copies instead of planner-sensitive broad scans.
- `First()` and `Last()` should be core ordered retrieval shortcuts. They should accept an optional count, for example `First()`, `First(10)`, `Last()`, and `Last(10)`.
- Retrieval shaping should support `skip`, `take`, ordering direction, de-duplication policy, and `Bookmark` at condition-terminal execution points because many LibraDex callers will likely be higher-level systems generating canned but partially dynamic calls rather than humans fluently chaining query objects.
- Query descriptor objects may still be useful internally or behind condition-terminal execution, but root index methods with optional `skip`, `take`, direction, and bookmark parameters should not return as a public grammar.
- `Bookmark` is the preferred term for continuation/resume state. It restores a useful indexed-file concept without hiding it behind vague paging language. A bookmark can carry last key, last identity/tie-breaker, direction, query shape/version, route/shelf hints, and index generation/version for stale detection.
- `Bookmark` should accelerate scan-backed retrieval by resuming near the previous shelf/route position. It can also accelerate indexed retrieval by tightening the effective key extent; for example `Between(a, b, bookmark)` can treat the bookmark key as the effective lower or upper boundary when it is inside the requested extent.
- Offset-style `skip` is still useful and familiar, but large offsets are inherently walk-past-N unless LibraDex adds route/shelf count metadata. Bookmark paging should be the preferred efficient continuation model.
- Physical index sort direction and query traversal direction are separate axes. The physical default should be ascending, while readers/queries should still support ascending and descending traversal over any index.
- `IndexSortDirection.Ascending` and `IndexSortDirection.Descending` describe optional physical storage/projection direction. `QueryDirection.Ascending` and `QueryDirection.Descending` describe caller traversal direction.
- Descending physical storage should be treated as an optional workload optimization, not the default. Ascending physical storage with descending query traversal should still be supported, even if it requires reverse traversal or a less optimal implementation until specialized descending projections exist.
- Value reversal is not sort direction. Reversing the value enables suffix-style lookup by turning suffix retrieval into prefix retrieval over a reversed projection. Sorting descending changes traversal/order over a projection without reversing the logical value.
- String projection should be modeled as multiple orthogonal axes: representation (`Exact`, `Folded`, `SortKey`), value projection (`Forward`, `Reversed`), and physical sort direction (`Ascending`, `Descending`).
- Reversed exact and reversed folded projections are straightforward suffix accelerators. Reversed sort-key projection needs validation before promising semantics, because reversing sort-key bytes may not be equivalent to reversing text and then generating a sort key.
- Maintained sub-indexes should own projections such as folded text, sort keys, reversed values, GUID segment/text projections, and structured date parts. A sub-index is a maintained projection under one logical index, not a separate user-visible index by default.
- Separate visible indexes should be reserved for independent lifecycle, identity sets, update policy, or a genuinely different logical key. Developers should not have to create separate visible indexes merely to get normal lookup intent such as no-case, suffix, GUID segment, or date-part retrieval.
- Abraxas index creation and condition building should be treated as one aligned design source. Abraxas currently emits selector SQL for index creation and condition SQL for retrieval, then tries to force SQLite to activate the matching physical index variant. LibraDex should not recreate that SQL-recognition dependency. It should model selector/projection shape as typed metadata first, then let condition translation target the matching projection directly.
- The first LibraDex shape descriptor slice is `catalog.Indexes["group"]["name"].Shape...`. It is descriptor-only for most projection forms and does not yet drive general physical storage. It can express scalar exact projections, string `Exact`/`FoldedText`/`SortKey` projections, forward/reversed byte directions, physical ascending/descending storage intent, GUID exact/segment/text projections, and date exact/structured projections. The current physical exception is the narrow `LibraDexStringScalar8Index` proof for exact, folded, and sort-key `VS8` string storage.
- This descriptor layer is the intended bridge between Abraxas-style selector fluency and LibraDex physical indexes. Future physical creation should consume the same descriptor that condition translation uses, so `Prefix`, `Suffix`, no-case point lookup, no-case range lookup, GUID segment/text lookup, and structured date-part lookup can ask for a maintained projection by semantic kind instead of by string matching.
- `catalog.Indexes.Create(shape)`, `.Open(shape)`, and `.CreateOrOpen(shape)` are the first descriptor-driven catalog factory path. They currently support scalar-compatible generic shapes and return strict non-generic `IIndex` handles. Shape-driven created handles expose `IIndex.LogicalShape` at runtime so planners can inspect projection intent without parsing names or SQL-like text.
- Composite-key descriptor support exists through `Shape.Composite<TIdentity>(...)` and `LibraDexCompositeKeyPart`. It captures ordered part names, part CLR types, part key families, string/GUID/date projection flags, and unique-over-composite intent. It now drives an in-process routed-component proof for condition execution; persisted composite mini-router storage and durable part metadata are still pending.
- Programmatic composite key values now have an explicit `LibraDexCompositeKey` container. `LibraDexCompositeKey.Of(...)` supports concise positional callers, while `LibraDexCompositeKey.Named(LibraDexCompositeKey.Part(...))` supports generated callers that want shape-name validation before physical encoding.
- The durable catalog metadata still needs to be widened before full descriptors can be rehydrated after reopen. The current slice persists the existing key/identity families and projection flags, while byte direction, physical sort order, and the projection list remain runtime descriptor metadata.
- GUID exact lookup should remain a 16-byte key fast path. Abraxas shows that GUID text-like operations can still be supported over 16-byte storage by deterministic byte/nibble operations rather than by storing GUIDs only as strings.
- GUID criteria should include exact `Find`, `Prefix`, `Suffix`, `Contains`, `Matches`, `Segment`, and `Slice`-style retrieval. Segment/text projections can make some of these fast-path; otherwise they may be scan-backed over exact GUID bytes with nibble masks.
- Date criteria should include exact chronological retrieval plus structured date-part retrieval such as year, year range, month, month set, day, year-month, year-month-day, weekday, quarter, and common calendar predicates. The design should follow the Abraxas packed-numeric date model rather than text formatting or query-time parsing.
- Abraxas and similar higher-level systems should remain responsible for converting object/member values into LibraDex-supported key classes. LibraDex should own fast lookup, maintained projections, and typed scan predicates over its limited key classes, not become a general object expression/conversion layer.

Aggregate and return-shape scaffold captured 2026-05-18, superseded 2026-05-20:

The May 18 aggregate, positional, grouping, and return-shape notes are parked until the adopted Abraxas condition/index builder pass proves which terminal shapes are needed. Do not implement these names or examples directly from this section.

- Aggregates are a separate public-surface concern from materialized retrieval. They should avoid identity materialization and should expose intent directly instead of requiring callers to write SQL-shaped aggregate expressions.
- Minimum aggregate facades should include `Count`, `Sum`, and `Average`. `Min` and `Max` should also be included in the aggregate design because ordered indexes can often answer them cheaply.
- Count should be a condition-terminal shortcut rather than a direct all-index or index-aggregate facade. `condition.Count(...)` preserves no-materialization intent without reviving a second retrieval grammar.
- Statistical/value aggregates should eventually hang from condition-terminal operations so the API does not blur materialized retrieval with computed values or reintroduce direct index verbs. Example target shape should be condition-scoped rather than `index.Aggregates.Count.Between(...)`.
- `Sum`, `Average`, `Min`, and `Max` should aggregate keys, not identities. In LibraDex semantics, identities identify records; summing or averaging identities is usually meaningless even when the identity type is physically numeric.
- `Median` and `Percentile` should be treated as aggregate/value operations, not tuple retrieval. They may return a key-like value that does not correspond to a stored tuple when continuous/interpolated semantics are used.
- Aggregate defaults should operate over matching tuples because tuple cardinality matches retrieval semantics. For duplicate-key indexes, `Count.Find(key)` counts matching identities/tuples by default.
- Distinct aggregate behavior should be explicit through an enum parameter rather than a boolean. Prefer a shape like `AggregateScope.Tuples` and `AggregateScope.DistinctKeys`; avoid unclear call sites such as `distinct: true`.
- Retrieval also needs explicit duplicate-key shape control, but it should be expressed as condition-terminal result shaping rather than per-call direct index retrieval options.
- Enums are preferred over boolean parameters for public API choices because they read better in code review and are easier to evolve.
- Return shape is its own public axis, but the active public surface is identity-first because multi-criteria composition across indexes does not have one coherent key type. Keys and tuples can be reintroduced as condition-terminal shapes when their projection semantics are settled.
- Root index retrieval methods such as `index.Between(a, b)` and `index.Find(key)` are retired. Retrieval criteria should be captured by the condition builder, then materialized or streamed through terminal condition operations.
- Prefer criteria-first, result-shape-last retrieval syntax at the condition level. The condition captures key criteria, and terminal operations choose identities, groups, counts, and future key/tuple projections without misleading forms such as `index.IDs.Prefix("er")`.
- Use `IDs`, not `Ids`, for the short public member because `Ids` visually reads like `lds`. Use full `Identity` / `Identities` in types and documentation where conceptual precision matters.
- Criteria over identities should be explicit and separate from key criteria, for example a future `WhereID` / `ByID` surface. Identity criteria are scans unless identity is part of the physical key/composite key or LibraDex maintains an identity-addressable projection; this is acceptable and no worse than comparable B-tree/SQL behavior.
- `First`, `Last`, and `Middle` are positional retrieval operations, not aggregates. They should be condition-terminal operations over the matched set, not direct index facades.
- `Middle` should return real indexed entries from the center of the ordered match set. It is not a mathematical midpoint and not necessarily a statistical median. Its public grammar should be criteria/condition-scoped rather than `index.Middle.Between(...)`.
- Multi-item `Middle(count)` should select a centered window of actual stored entries and then return that window in normal query order unless `QueryDirection.Descending` is requested. Selection/candidacy order is an internal implementation detail and should not leak into return ordering.
- Even-result and duplicate-center ambiguity should be controlled by an enum, not a boolean. Prefer a shape like `MiddleBias.LeftBiased` and `MiddleBias.RightBiased`. Bias selects the center anchor/window; query direction controls final return order.
- Key projection is not redundant. On projection-rich string indexes such as exact + folded + sort-key, the lookup may use a folded/no-case projection while returning the exact stored key forms that matched. This separates lookup projection from returned key representation while preserving criteria-first grammar.
- The public model should distinguish lookup projection, stored key representation, and returned result shape. This is especially important for strings, GUIDs, and structured date keys.
- Deeper controls for which key representation to return, such as exact versus folded versus sort-key, can be designed later. The immediate decision is that `Keys` retrieval is valuable and should not be dismissed as merely returning the query value.
- LibraDex indexes should serve both as object lookup structures and as value retrieval structures. Higher-level systems such as Abraxas should be able to use `Keys`, aggregate, and criteria APIs for real work without reaching back to object payloads unless object materialization is actually needed.
- This is a deliberate contrast with SQL/B-tree systems, where index-contained values are often only exploited when very specific covering-index SQL text and planner behavior line up. LibraDex should make value-from-index retrieval explicit, discoverable, and reviewable.
- Grouping is a retrieval/result-shaping concern adjacent to aggregates, not merely a scalar aggregate feature. Grouping introduces keyed groups with per-group counts, aggregate values, representative tuples, keys, or identity lists.
- Grouping should be condition-first and identity-group scoped. The preferred shape is `condition.Groups.By(index)`, where the condition supplies candidate identities and the selected index supplies group keys. Avoid `Groups.ByKey` as the canonical public grammar because it implies a parallel `ByIdentity` menu and keeps the older direct index-query surface in the center.
- Grouping should be useful beyond SQL-style `GROUP BY key`. It should support duplicate-key grouping, projection grouping, and partial-value grouping such as prefix, suffix, folded string, sort-key, date part, GUID segment/slice, and numeric bucket grouping.
- The group key type may differ from the physical index key type. Examples include date key grouped by year, string key grouped by folded form, GUID key grouped by segment, or numeric key grouped by bucket.
- If a grouping request is valid but semantically degenerates to singleton groups, LibraDex should detect that and route internally to the cheaper retrieval path while preserving the grouped public result shape. Example: grouping by full key on a unique-key index yields groups with `Count == 1`.
- Grouped APIs should be streaming-first. A caller should be able to iterate one group at a time without forcing dictionary/list materialization for the whole result set.
- Streaming group readers should expose group-level movement. A caller should be able to inspect group metadata, then enumerate the group or skip directly to the next group without row-by-row drain when the group is extent-backed.
- `OpenReader()` now has a dictionary-backed correctness implementation over the connected grouped materializer. It exposes `Current.Key`, `Current.Count`, `Current.Items`, `MoveNextGroup()`, and `SkipGroup()` so the public grouped-reader shape is executable; true extent-backed group skipping remains a future physical optimization.
- `LibraDexConditionEndCondition.Groups(resolveIndex).By(index)` is now the adopted grouping bridge for new call sites. It exposes the duplicate/singleton/count filters, key/count ordering, group-level take, metadata, `ToList`, `ToDictionary`, counts, representatives, first/last groups, first/last metadata, and `OpenReader`. The older `LibraDexIdentityCondition.Groups.By(index)` bridge has been deleted.
- Condition grouping now has immutable count filters: `WhereCountAtLeast(...)`, `WhereCountAtMost(...)`, `WhereCount(...)`, `Duplicates()`, and `Singletons()`. These filters are applied before metadata/member materialization and are the first non-SQL group-filter vocabulary.
- Condition grouping now has immutable group ordering, item ordering, and limiting: `OrderBy(LibraDexGroupOrder.KeyAscending/KeyDescending/CountAscending/CountDescending)`, `OrderItemsBy(QueryDirection.Ascending/Descending)`, `Take(count)`, and `TopDuplicates(count)`. Key order is the grouping index order; item order controls identities inside each group; count order answers metadata questions such as largest duplicate groups.
- Condition grouping now exposes edge-group retrieval: `FirstGroup()`, `LastGroup()`, `FirstMetadata()`, and `LastMetadata()`. These are retrieval operations over whole key groups, not scalar aggregates, and directly support questions such as "all identities at the lowest received date".
- Group materialization should be explicit and secondary to streaming. Current materializers include `ToDictionary()`, `ToList()`, `Counts()`, and `Metadata()`. Later dense helpers such as `ToArrays()` can be added when a paired group-key representation keeps meaning intact.
- Avoid making `[][]` the primary grouped return shape because it loses group keys unless paired with another array. Dense array materializers can exist later as performance helpers, but the main API should keep group keys attached.
- Group filters should provide the SQL `HAVING` capability without requiring SQL terminology. Prefer explicit fluent filters such as `WhereCount(...)`, `WhereKey(...)`, `WhereFirst(...)`, `WhereLast(...)`, and eventually `WhereAggregate(...)`.
- Group filtering should expose or internally track whether it is extent-backed, summary-backed, or scan-backed. `Count`, `First`, `Last`, and `Middle` filters can often be answered cheaply when group extents/counts are known; `Sum` and `Average` may require maintained summaries or per-group scans.
- Group order and item order are separate axes. LibraDex can now return condition groups ascending or descending by group key/count and can return identities within each group ascending or descending by grouping-index traversal order.
- Groups should expose useful metadata and representatives without forcing enumeration: `Key`, `Count`, `FirstIdentity`, `LastIdentity`, `MiddleIdentity`, `MinKey`, and `MaxKey` are likely candidates. Current condition grouping metadata includes `Key`, `Count`, `FirstIdentity`, and `LastIdentity`.
- Grouping should return populated groups by default. Synthetic bucket grouping may later offer empty-bucket inclusion, but empty groups should not be the normal index grouping behavior.
- Prepared grouping specs may be useful for reusable partial/projection grouping, similar to prepared `InSet`: for example, prepare prefix length, bucket width, date part, or GUID segment grouping once and reuse it across criteria.
- Group bookmarks should be considered separately from row bookmarks. Grouped streaming needs continuation at the group boundary and within a group, especially when callers skip groups or resume after partial group enumeration.

Parked public-surface topics for expanded discussion after Abraxas builder adoption:

The topics below remain useful design prompts, but they are not active API commitments. Re-evaluate each through the adopted condition/index builder permutations before adding public names or execution paths.

- Ordering and direction rules. Query direction should change traversal direction, not force sorting or physical reordering. Reverse traversal should be supported where the shelf/router structure can walk the index in the requested direction. Current cursor-level descending support is a buffered correctness fallback, not the final physical reverse cursor. Diagnostics should identify when a requested order is fast-path, projection-backed, reverse-traversal-backed, buffered, scan-backed, or sort-backed.
- Distinct semantics. Distinct behavior needs one coherent design across retrieval, keys, identities, aggregates, and grouping. It should use explicit enums instead of booleans and should avoid contradictory combinations such as asking for distinct keys while returning ambiguous identities without a first/last/middle rule.
- Set operations and multi-criteria identity composition. LibraDex should support `Union`, `Intersect`, and `Except` over comparable query streams, likely ordered by identity or tuple order where possible. Normal cross-index lookup is identity composition inside one `IdentityGroup`. Cross-group composition is left to caller-owned orchestration, including parallel operations, because LibraDex should not infer shared identity meaning or result shape across groups.
- Multi-criteria planning should decide when to compose independent identity streams and when to use a composite index directly. A condition such as first name + last name + birth date may be answered by separate indexes with `And(...)`, but a matching composite index can answer leading-part and full-key constraints more directly.
- Composite indexes are required public API, not a convenience. LibraDex needs one ordered key made from multiple typed parts so callers do not hand-concatenate values or invent delimiter/encoding rules.
- Composite uniqueness is the important contract. `IndexKeys.Unique` over a composite index should mean the full encoded composite key is unique, for example `(tenantId, username)` or `(orderId, lineNumber)`, while individual leading parts may repeat freely.
- Composite index retrieval should support full-key exact lookup and leading-part retrieval. Examples include `Find(tenantId, username)`, `Prefix(tenantId)`, `Prefix(tenantId, lastName)`, and bounded ranges over complete or leading-compatible composite keys.
- Programmatic composite keys should use an explicit `CompositeKey` or equivalent builder so higher-level systems can construct keys dynamically. C# tuple convenience can exist for hand-written code, but it should not be the only supported composite-key shape.
- Composite key parts should reuse LibraDex's opinionated key classes and projections: numerics, chars, dates, GUIDs, fixed/variable bytes, and strings with exact/folded/sort-key/reversed options. This keeps composite ordering deterministic and avoids query-time conversion ambiguity.
- Criteria-driven delete/update. LibraDex mutation should primarily exist within retrieval/cursor context rather than as a detached SQL-style `UPDATE WHERE` surface. A retrieval cursor already owns the current key, identity, route/shelf position, duplicate-run context, traversal direction, and extent/bookmark state, so update/delete can avoid rediscovering the same tuple.
- Descriptor scaffold now exposes criteria-scoped mutation intent through `IIdentityCriterion.Mutate.Delete()` and `IIdentityCriterion.Mutate.SetKey(...)`. `Delete().Execute()` is connected for one primitive leaf whose backing index implements `IIdentityPrimitiveMutator`; routed composite indexes implement that bridge for `All`, exact composite key, and `CompositeMatch` deletes, and all generic fixed scalar shapes implement it for all/range/boundary/exact/membership/multirange deletes. Fixed scalar delete now marks deleted slots with the fixed sentinel and normalizes before staging the compact shelf rewrite, so persisted shelves stay tombstone-free without a separate reclaimed-offset ledger. Cursor-local delete is connected through `LibraDexRangeReader<TKey,TIdentity>.DeleteCurrent()` for every generic fixed scalar shape; it invalidates current access, adjusts the retained slot interval, and allows the next move to continue at the tuple shifted into the deleted slot. Scalar and composite `SetKey(...).Execute()` are connected for one primitive leaf whose backing index implements tuple capture and exact tuple mutation; the operation captures old key/identity tuples, inserts or verifies replacement tuples, then deletes only exact old tuples. Cursor-local `LibraDexRangeReader<TKey,TIdentity>.SetKey(newKey)` is connected for every generic fixed scalar shape through an owning-index exact rekey callback; the retained range remains a traversal snapshot, current access is invalidated after mutation, and the next move skips the stale original current row. `LibraDexConditionEndCondition` now exposes terminal `Delete(...)`, `SetKey(...)`, `DeleteFrom(...)`, and `SetKeyOn(...)` convenience methods over resolver delegates or opened-index dictionaries.
- Cursor-local mutation exposes explicit operations such as `SetKey(newKey)`, `DeleteCurrent()`, and `Delete()` on the current tuple. `SetKey` is the main update operation because LibraDex is an identity index; changing a key is logically remove old key/identity tuple plus insert new key/identity tuple. Changing an identity should be treated as rarer and more constrained because it may collide with uniqueness or identity-order invariants.
- Mutation methods should not require a separate mandatory mutable cursor mode in the core DX. The explicit `SetKey`/`Delete` call is enough of a mutation gate, and requiring an upfront mode would likely cause developers to do one read pass to check results and then repeat the same query for mutation.
- Cursor mutation should be traversal-stable. The cursor walks the original candidate sequence; mutating or deleting the current tuple must not cause that tuple to be visited again, and must not cause the next original candidate to be skipped. Internally this implies capturing or preserving the next-position before applying the current mutation.
- Cursor mutation should apply logically immediately, while batch mode controls durability cadence. `BatchManager` affects when file-backed work is committed; it is not a transaction and does not imply rollback or delayed cursor visibility by default.
- Direct identity/key targeted helpers may still be useful when the caller knows enough to avoid a search. Scalar and composite `Rekey(identity, oldKey, newKey)` are now connected by verifying the old exact tuple, inserting or verifying the replacement exact tuple, and deleting only the old exact tuple. Scalar and composite `Rekey(identity, newKey)` are scan-backed today and can later be optimized by a maintained reverse identity lookup without changing the public call shape.
- Diagnostics and plan metadata. LibraDex should not require SQL-style `EXPLAIN` as normal development flow, but public readers/results should be able to expose whether a call used fast path, projection path, scan path, reverse traversal, group skip, prepared set membership, or other important execution choices.
- Prepared reusable helpers. Prepared/compiled should not mean SQL text parsing or a general query planner. It should be limited to reusable runtime objects that remove real repeated work, such as prepared `InSet`, grouping specs, encoded prefix/suffix/projection values, bookmarks, or other reusable criteria components.

Stats / diagnostics / observability decisions captured 2026-05-18:

- Stats should be a first-class public API category because predictable performance and maintainability are part of LibraDex DX, not an afterthought.
- Prefer passive `Stats` surfaces first, such as `catalog.Stats` and `index.Stats`. Reserve `Telemetry` for future event streams, exporters, callbacks, or live tracing if those become necessary.
- Stats should cover modification information such as last modified timestamp, last insert/delete/rekey timestamp, total inserts/deletes/rekeys, commit count, and batch-related state.
- Stats should support developer-set markers, similar to a trip counter: `var marker = index.Stats.Mark();` followed later by `index.Stats.Since(marker)`. Marker deltas can report inserts, deletes, rekeys, commits, bytes written, shelf splits, route changes, reclaimed payload cells recorded/consumed, and other counters that happened after the marker.
- Catalog stats now expose `ReclaimedPayload`, a session-scoped snapshot of queued fixed-shelf payload cells plus cumulative recorded and consumed cell counts. This is intentionally not index-attributed yet because the current ledger is keyed by durable shelf offset and is not persisted across reopen.
- Shelf metadata should distinguish physical entries from live entries across fixed and varlen families. The first executable contract exposes compact-shelf aliases now; tombstone-aware mutation should later make `DeletedItemCount` and varlen `PayloadBytesDeleted` non-zero before commit/repack normalization.
- Stats should expose physical layout information through snapshots rather than forcing all metrics to be live and cheap. Likely layout metrics include router count, shelf count, shelf density, min/max/average shelf fill, split count, reusable capacity, file bytes owned by index, and bytes by routers/shelves/free/reusable regions.
- Operational stats should include commit count, write count, bytes written, `SetLength` count, batch enabled state, pending batch mutation counts where available, and last commit timestamp.

- Stats APIs should support both catalog-level rollups and index-level detail. Catalog stats can answer "what changed in this file/group", while index stats can answer "what changed or degraded in this index".

- Cursor readers are the default for analysis, filtering, skipping, and datareader-style iteration because they expose row-local spans without allocating per result row.
- Fixed-width identity range helpers may copy into caller-owned spans when that is the densest, lowest-friction representation.
- Variable-length bulk reads should use disposable disconnected buffers over pooled flat payload arrays plus offset/length metadata, not `byte[][]`.
- Varlen key buffers, identity buffers, and tuple buffers should expose indexed spans/memory, flat payload spans/memory where applicable, copy helpers, explicit single-row `ToArray(index)` materialization, and allocation-free struct enumeration.
- Tuple buffers should keep key and identity payloads separated but row-ordinal aligned, so callers can inspect keys, identities, or full tuples without materializing nested arrays.
- Buffer work should now pause until the public naming/factory layer is reviewed; do not add more result types unless a real DX gap is identified.

## 10. Shape Naming Rules

LibraDex should use `shape` as the standard term for the physical key/identity family that drives specialized shelf, router, codec, and benchmark code paths.

The project should be strict about `identity` terminology. The right-hand member of a shelf item is an identity, not a general value. Internal code, benchmark artifacts, and future public documentation should prefer `identity` consistently so the design intent stays clear.

Shapes are expected to be concrete and clone-friendly. Early optimized shapes should be copied and specialized in code for the next shape rather than prematurely generalized behind one universal hot-path abstraction.

Full shape names use this pattern:

- `[KeyDataClass][KeyWidth][IdentityDataClass][IdentityWidth]`

Abbreviated shape names use this pattern:

- `[KeyClassChar][IdentityClassChar][KeyWidth]-[IdentityWidth]`

Class letters:

- `S` = Scalar
- `F` = Fixed
- `V` = VarLen

Width means persisted byte width, not developer-facing logical width. If a developer-facing `uint` is projected into an 8-byte persisted identity field, the shape width is still `8`.

The first concrete shape is:

- Full name: `Scalar8Scalar8`
- Abbreviation: `SS8-8`

Examples for the same convention:

- `Scalar8Scalar16` -> `SS8-16`
- `Scalar8Fixed16` -> `SF8-16`
- `Fixed16Scalar8` -> `FS16-8`
- `Fixed16Fixed16` -> `FF16-16`

Varlen abbreviations should stay simple when one side is variable-length:

- `VarLenScalar8` -> `VS8`
- `Scalar8VarLen` -> `SV8`

When both sides are variable-length, the project should define that abbreviation explicitly at the time the first such shape is introduced rather than guessing now.

## 11. Scalar Encoding Invariant

Scalar numeric shapes must persist fields in canonical sortable form, not in native in-memory layout.

Global rules:

- Native machine endianness is irrelevant to persisted scalar ordering.
- LibraDex should never rely on current `.NET` little-endian machine layout as the durable sort encoding for scalar fields.
- Persisted scalar numeric fields should be encoded once into sortable canonical form, then compared in that encoded form during shelf and router work.
- Query inputs for scalar shapes should also be encoded into the same sortable canonical form before entering hot compare loops.

Unsigned scalar numeric fields:

- Persist as big-endian bytes.
- Big-endian byte order is the canonical sortable form for unsigned scalar numerics.

Signed scalar numeric fields:

- Persist as order-preserving normalized big-endian bytes.
- Signed scalar values require a monotonic normalization step before big-endian persistence so lexicographic byte order matches signed numeric order.
- The normalization detail belongs to the scalar codec/profile, not to generic shelf logic.

Cost model:

- Stored scalar items pay the normalization/encoding cost when they are persisted.
- Scalar query inputs pay the normalization/encoding cost once per operation before shelf/router comparisons.
- Hot compare paths should not repeatedly decode or renormalize persisted scalar bytes.

This invariant is one of the reasons the scalar/fixed/varlen shape distinction matters:

- Scalar shapes often need explicit sortable encoding rules.
- Fixed non-scalar shapes may already define ordering directly over bytes.
- Variable-length shapes may need different ordering, prefix, and separator rules.

## 12. Router Model

The initial router target is a direct file offset. The `DataKernel` owns file layout and offset validity, but router route slots persist direct target offsets for fast routing.

There is one router contract. Root routers, compressed routers, expanded routers, and future multi-byte routers all use the same 10-byte route slot. Route compression and direct-index lookup are states/capabilities of that contract, not separate persisted router formats.

The initial persisted route slot is `10` bytes:

- `1` byte prefix-start.
- `1` byte prefix-end.
- `8` byte target file offset.

Offset `0` is reserved for the superblock and is never a valid route target.

A router can use range compression by mapping multiple prefix byte values to the same target offset. As growth refines a route, the router can split a broad range into narrower ranges without changing the parent router.

A fully expanded 1b-router has `256` single-byte ranges using the same route-slot format. At that point, lookup may use direct index-style discovery while preserving the persisted layout.

Routers may be preallocated to their maximum route capacity when that reduces future growth work or when a shelf transmorphs into a router inside already-allocated shelf space.

The root router is a 1b-router at key depth `0` and is created fully expanded from birth. It occupies a 4 KiB router page, stores `256` self-range route slots, sets the direct-index flag, and leaves route target offsets as zero until child shelves or routers exist.

The first router page reserves a `64` byte header, `2,560` bytes for `256` route slots, and `1,472` bytes of slack for future router-local metadata such as hot-route hints, prefetch hints, checksums, or density summaries.

When a 32 KiB `SS8-8` shelf transmorphs into a 4 KiB router, the remaining extent space is a router micro-arena candidate. The transformed router occupies arena page `0`; up to seven more 4 KiB routers can be placed in that same former shelf extent without growing the file. Arena membership is stored as relative router metadata so a whole router block can be relocated later without rewriting absolute arena relationships.

Router micro-arena allocation is local-biased but not locality-exclusive. A request should prefer free router pages in the transformed shelf's own arena, then use any eligible same-index arena, then append a normal router page when all registered arenas are exhausted. This preserves locality when cheap while avoiding unnecessary file growth.

The first router micro-arena read cache is a session-scoped single-entry cache. An explicit arena-aware walker can load a full 32 KiB router arena on first touch, then serve later router page and router magic reads from that cached block. The cache is conservatively invalidated on every session commit.

Arena-aware route walking should be policy-gated rather than unconditional while the cache is single-entry. Release evidence shows repeated same-arena routing improves materially and mixed direct+arena routing improves, but cold one-off routing pays the 32 KiB first-touch cost and alternating arena routing becomes byte-heavy.

The first policy gate lives at explicit operation mode. `Scalar8Scalar8RouteReadPolicy.Uncached` preserves the existing classified walker; `Scalar8Scalar8RouteReadPolicy.PreferArenaCache` opts into arena-aware reads for operations that expect locality.

Arena-aware reads should load a whole router micro-arena only when first touching arena page `0`, the natural top-down entry router for a transformed shelf. Reads for non-entry arena pages should use the normal single-router read unless that arena is already cached.

Multi-byte routers still use the same route slot contract, but should be intentionally route-limited. Their purpose is reducing routing depth, not exploding into a full direct table over all possible multi-byte combinations.

## 13. Shelf Growth Model

Shelf shape is part of the physical index profile. LibraDex should intentionally choose different shelf layouts, shelf sizes, search thresholds, and split policies based on encoded key size, identity size, mutability posture, and expected range-scoop behavior. This is a feature of the design, not accidental complexity.

Different shelf shapes should not be forced through one generic hot-path implementation. Outer APIs may be generic and low-friction later, but hot shelf byte views should remain concrete where that protects allocation behavior, call-chain depth, address math, and predictable generated code.

Fixed-size item shelves and variable-length shelves are different contracts. Fixed scalar shelves should optimize for predictable capacity, direct projection, bounded rewrite size, and cheap inserts. Variable-length shelves may need a different split/extension model because payload sizes and slack economics are different.

Uniqueness policy belongs to the index, not to an individual shelf shape. Shelves enforce the active index policy, but the rule itself is part of index metadata and behavior, similar in spirit to unique versus non-unique SQL indexes.

Shelf layout information exists at three different levels and should not be collapsed into one persisted header:

- **Runtime shape constants:** compiled into the concrete shape code and not stored in every shelf. Examples include slot size, item payload size, key width, identity width, field offsets, and scalar encoding rules.
- **Index profile metadata:** persisted once per index/profile and used on reopen to select the correct concrete shape code and policy. Examples include shape id, uniqueness mode, shelf extent class/size, and profile/version ids.
- **Shelf header bytes:** persisted inside each shelf and limited to fields that vary per shelf or are needed for local validation/recovery. Examples include magic, format version, flags, item count, and item write offset.

Shape-specific layout helpers may expose many constants and helper methods at runtime, but that does not imply those values belong in every shelf's persisted bytes.

When an incoming shelf item or mutation does not fit, LibraDex first tries a normal shelf split.

Normal split behavior:

- Some percentage of the original shelf remains in the original shelf.
- The remainder moves to one new shelf.
- The incoming item is placed into whichever of the two shelves owns its sorted position.
- The owning router is updated to route to both shelves.
- The expected write shape is dirty original shelf, new shelf, and dirty owning router.

When the owning router is full, LibraDex uses a transmorphic shelf split.

Transmorphic split behavior:

- The owning router is not dirtied for expansion.
- The shelf's existing storage location is rewritten as a child router.
- The old shelf data plus incoming item are redistributed into two shelves.
- The parent route remains valid because it still points to the former shelf location, now interpreted as a router.
- The expected write shape is dirty former shelf location as router plus two shelves, with no parent-router rewrite.

This model is intended to avoid B-tree-style upward split cascades while also avoiding file-size explosions from abandoned shelf extents.

Deterministic split policy should be cheap enough to run during mutation:

- Prefer a normal split when the owning router can represent a useful boundary.
- A normal split rewrites the existing shelf for one side and appends exactly one new shelf for the other side.
- Use fixed profile thresholds for minimum side occupancy, maximum imbalance, and maximum prefix-depth search; do not make hot mutation choose by trial benchmarking.
- Use transmorphic split only when the current route cannot represent a useful boundary or when the next useful boundary requires the old shelf location to become a child router.
- Treat route-depth growth as acceptable when it preserves dense ordered shelf scans and keeps logical throughput near raw baselines.
- Evaluate any split-policy change by identities/items per second, bytes per logical item, write/read calls, `SetLength`, and file growth, not by resemblance to B-tree or other existing index families.

Current `SS8-8` split audit:

- `SplitRoutedScalar8Scalar8ByRootPrefix` matches normal split intent: it rewrites the original shelf, appends one right shelf, and rewrites the root router.
- `SplitRoutedScalar8Scalar8ByShelfTransform` matches transmorphic split intent: it rewrites the old shelf offset as a child router and appends two replacement shelves, with optional deeper router chaining when the next prefix bytes remain clustered.
- `TrySplitRoutedScalar8Scalar8ByParentRoute` now matches normal split intent: it prevents a transform by refining parent-router routes, rewrites the original full shelf as the left split side, appends one right shelf, and rewrites the parent router.

### First Fixed Scalar Shelf Shape

The first fixed shelf implementation target is `FixedScalarShelf16`.

`FixedScalarShelf16` is a mutable fixed-size shelf for an `8` byte scalar encoded key and an `8` byte scalar identity value. Smaller developer-facing scalar values such as `int` or `uint` can still be projected into the 8-byte key or identity field, accepting the small built-in slack in exchange for natural 64-bit alignment and simpler byte paths.

The first fixed scalar shelf is non-expandable. Shelf size is fixed by its allocation class. A fixed-size shelf should split when it cannot fit another slot plus item, rather than extending in place. Variable-length shelf shapes may revisit extension later, but fixed scalar shelves should keep extent size bounded and predictable.

The initial target shelf size for small fixed scalar shelves remains `32 KiB` as the first mutable scalar baseline, but it is now a baseline rather than a settled optimum. The shelf size should be proportioned to item shape so small scalar indexes do not accumulate excessive permanent slack. Larger fixed shelves may be used for wider fixed shapes or range-heavy profiles, and smaller fixed shelves may be considered when distributed multi-shelf locality dominates.

Current `SS8-8` shelf-size measurements separate three views:

- Equal-work single-shelf: same item count, insert order, lookup keys, and range starts across shelf sizes.
- Full-capacity single-shelf: each profile filled to its maximum item count to show capacity economics and worst-case search/shift growth.
- Multi-shelf equal-work: many shelves end-to-end in one byte arena to expose locality and aggregate traversal effects.

The current size-sweep evidence shows:

- Cached equal-work single-shelf reads are mostly flat across tested sizes when item count is controlled.
- Cached full-capacity single-shelf reads begin to show higher cost after 32 KiB.
- Cached full-capacity multi-shelf reads rise steadily with shelf size because larger arenas put more pressure on locality.
- `DataKernel` file-read throughput improves with larger shelf extents, with diminishing returns after about 32 KiB.

This makes 32 KiB the best current default for `SS8-8`, not because it wins every microbenchmark, but because it is the first conventional power-of-two size with strong DataKernel read throughput while avoiding the larger cached-read cost jump visible at 48/64 KiB. Keep 24 KiB and 16 KiB available as profile candidates; 24 KiB is a serious latency/locality candidate, and 16 KiB is useful when distributed cached reads dominate and extra split/router pressure is acceptable.

The first fixed scalar physical layout uses pre-partitioned regions:

- Header at the beginning of the shelf.
- Fixed maximum-width sorted slot array after the header.
- Fixed item payload array after the slot array.
- Each slot stores a `ushort` byte offset to the physical item payload.
- Each item payload is exactly `16` bytes: `8` byte encoded key followed by `8` byte identity.
- The shelf is full when `itemCount == maxItemCount`.

The fixed slot array region and fixed item region are appropriate because `SS8-8` has a known item width, known slot width, known shelf extent size, and known maximum item count. Unused shelf capacity still exists inside the fixed extent either way; the difference is operational simplicity, not file-size savings.

The two-ended page pattern used by many B-tree/database pages should be reserved for shelf shapes that benefit from it, especially variable-length shapes. It is valuable when cells have variable sizes, deletes create fragmented payload regions, or a page must support multiple record shapes. It is not required for the first fixed scalar shelf.

The first persisted shelf header should stay minimal. Runtime constants such as slot size `2`, item size `16`, key size `8`, identity size `8`, maximum item count, and fixed shelf extent size should be known from the shape/index profile rather than repeated in every shelf header.

The sorted slot array exists to balance write/build cost against read cost. Inserts write one 16-byte item payload, then shift only sorted `ushort` slots. This avoids moving full item payloads on every insert and keeps bulk insert/build behavior acceptable enough that developers can reach the read-speed benefits.

Slot offsets intentionally avoid `itemBase + itemIndex * itemSize` in the first mutable shelf. A 16-bit byte offset keeps address calculation direct and constrains the shelf to a hardware-friendly in-shelf range. This favors concrete, small shelf families over one generic item-indexed shelf.

For a 32 KiB shelf with a small header, `FixedScalarShelf16` should hold roughly 1,800 items. The slot array for that count is only about 3.6 KiB, and the full shelf remains small enough that the slot indirection should be absorbed well by modern CPU caches. Binary search can reduce comparisons, but a linear scan over a properly sized shelf is expected to be competitive for small counts and useful for fail-fast behavior.

Shelf search policy should be internal and measurable:

- Linear scan is acceptable for small item counts.
- Binary lower-bound search is expected for larger point/range starts.
- Range scoop should locate the lower bound, then walk sorted slots linearly.

The mutable slot shelf is not the only possible read shape. A future packed/static shelf may store items physically sorted for maximum range-scoop locality after bulk build or compaction. The first mutable shelf prioritizes insert cost, bounded rewrite size, and realistic split economics before optimizing every read path.

### First Uniqueness And Ordering Rules

The first concrete shelf shape, `Scalar8Scalar8` / `SS8-8`, should use tuple ordering over `(key, identity)`.

Ordering rules:

- Primary sort key: encoded key.
- Secondary sort key: identity.
- Equal keys in a non-unique index are ordered by identity.

Index-level uniqueness modes:

- **Unique index:** key is unique for the index.
- **Non-unique index:** duplicate keys are allowed for the index.

Behavior under those modes:

- In a unique index, inserting an existing key does not require a second identity tie-breaker for conflict detection. The outer API may later choose whether that condition is surfaced as success, conflict, or another result shape, but the shelf/runtime should treat it as an index-level uniqueness outcome rather than as a new shelf-local rule.
- In a non-unique index, duplicate keys are allowed, but identities under the same key must still be distinct.
- In a non-unique index, inserting an already existing `(key, identity)` pair is a physical no-op because no mutation is needed.

LibraDex should distinguish between storage effect and API outcome:

- **Physical no-op:** the requested index state already exists, so no shelf/router/file mutation occurs.
- **Logical success:** the caller may still treat the operation as successful because the requested index state exists after the operation.

The shelf layer should eventually return a small structural outcome that lets outer APIs map behavior appropriately without forcing public semantics into the hot byte path too early.

## 14. Superblock And Index Directory

The `.lbdx` file begins with a superblock at file offset `0`.

The superblock should identify the file, record global format metadata, and provide or point to the index directory.

The index directory records the offsets where root routers for indexes start. A single `.lbdx` file may hold multiple indexes, so the superblock must provide a stable path to find each index root on reopen.

The practical index count can be capped. A generous default cap is `64` indexes per `.lbdx` file, which supports several dozen indexes over the same data without designing the superblock as a dynamic database.

The index directory should favor fixed-size slots. Each slot should hold routing-critical and reopen-critical fields such as state, flags, root-router offset, profile identifiers, item counts, generation/version fields, allocation-class identity, and an offset to any variable-length metadata.

The first fixed index-directory layout uses `64` slots of `128` bytes each, for an `8 KiB` directory. Each slot may include a fixed-width UTF-8 textual identity/name so common reopen, listing, and diagnostics paths do not need to chase variable-length metadata.

The first fixed slot layout is:

| Field | Offset | Size |
| --- | ---: | ---: |
| State | 0 | 1 |
| Flags | 1 | 1 |
| Reserved/padding | 2 | 6 |
| RootRouterOffset | 8 | 8 |
| MetadataOffset | 16 | 8 |
| ItemCount | 24 | 8 |
| Generation | 32 | 8 |
| KeyProfileId | 40 | 2 |
| IdentityProfileId | 42 | 2 |
| RouterProfileId | 44 | 2 |
| AllocationClassId | 46 | 2 |
| Name | 48 | 80 |

Variable-length index metadata, such as descriptions or extended codec/profile descriptors, should live in a second structure referenced by offset from the fixed-size index slot.

Unused index slots should be explicitly marked empty.

The first implementation may use a simple fixed-slot index-directory shape, but the design should not assume only one index per file.

The superblock is a special sparse/reserved region and should occupy a page-sized `4 KiB` region at file offset `0`. The fixed index directory should begin after it at offset `4096`, keeping the file-start metadata page-aligned and predictable.

Superblock metadata should be split between engine-owned metadata and developer-owned optional metadata.

Engine-owned metadata describes the `.lbdx` file and is maintained by LibraDex. Avoid generic last-modified fields that would encourage writes on every mutation or commit; if needed, use narrower semantics such as settings/config update time. `CreatedUtcTicks` is acceptable because it is written once.

Developer-owned metadata is optional, empty by default, and stored but not interpreted by LibraDex. Use short API-facing names:

- `DevIdentity`: developer/application identity string.
- `DevCustomText`: additional developer/application text string.
- `DevGuid`: developer/application GUID.
- `DevDate1`: first developer/application date value.
- `DevDate2`: second developer/application date value.
- `DevNumber`: one raw 8-byte developer/application numeric value, surfaced through compatible numeric projections.

Developer string fields are stored as fixed-width UTF-8 in the superblock layout, but API names should expose them as normal .NET strings. Changing developer metadata is a metadata/config update, not an index data mutation.

## 15. Deadspace And Reuse Policy

LibraDex should discuss deadspace and reuse now, but implement the general free-space manager later. The early runtime should remain append-first except where reuse is structurally part of the index design.

Durable terms:

- **Live extent:** a file extent currently reachable from the superblock, index directory, router graph, or shelf graph.
- **Retired extent:** a formerly live file extent no longer reachable after a successful commit.
- **Free extent:** a retired extent that the allocator is allowed to reuse.
- **Reuse candidate:** a retired extent that is known but not yet eligible or suitable for immediate reuse.
- **Allocation class:** a reusable size/shape class, such as metadata page, router page, small shelf extent, or large shelf extent.

Reuse tiers:

- **Structural reuse:** same-offset reuse required by the design. The main early example is shelf-to-router transmorph, where the former shelf location is rewritten as a child router so the parent route remains valid and no parent-router expansion is needed.
- **Class-compatible reuse:** reuse retired extents only for compatible allocation classes, such as router-sized pages for routers/metadata or large shelf extents for shelves of similar size. This should be defined before broad implementation but deferred until real split/growth patterns exist.
- **Compaction:** explicit maintenance that rewrites live structures to recover fragmented deadspace. This is not an early runtime behavior.

Early telemetry should make deadspace visible before a free-space manager exists:

- Bytes appended.
- Bytes rewritten in place.
- Bytes retired.
- Bytes reused.
- Live bytes estimate.
- Retired bytes estimate.

Code-review rule:

Every change that affects file allocation, extent sizing, split behavior, router growth, shelf growth, or metadata rewrite shape must be reviewed for deadspace/reuse impact. The review question is whether the change preserves future ability to support structural reuse, class-compatible reuse, and compaction without format breakage or syscall-pattern surprises.
